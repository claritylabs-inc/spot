# AGENTS.md

Guidance for coding agents in this repository. Read `CLAUDE.md` and, before Convex code changes, `convex/_generated/ai/guidelines.md`. Ground changes in the current code and preserve unrelated worktree edits.

## Testing and documentation

Prefer browser workflow QA for complex features. Do not write unit tests after writing code. An isolation test is justified only for a failure E2E cannot reliably catch, such as authorization, tenant isolation, webhook signatures, replay, leases, idempotency, fail-closed behavior, or a compact domain invariant; list failure modes before implementing an isolated system. `docs/testing/workflow-qa.md` owns the E2E coverage ledger and repeatable artifacts. Use Node 24.x. Keep `AGENT_TOOLS.md` synchronized with every material model-callable or MCP tool change. Update this file after major architecture changes. Use `dayjs` for new or touched date logic.

## Convex CLI safety

Conductor workspaces may inherit `CONVEX_DEPLOY_KEY` for an unrelated hosted deployment, which makes any `convex` CLI command (`dev`, `codegen`, `run`, `deploy`, `logs`…) target it instead of the local backend; on October 22, 2026 a bare `npx convex dev` pushed Spot over spot-content production. Start the local backend only through the Conductor run script (`CONVEX_AGENT_MODE=anonymous convex dev --local-cloud-port …`), and prefix every other Convex CLI command with `env -u CONVEX_DEPLOY_KEY -u CONVEX_DEPLOYMENT_TOKEN`. Agents never deploy; production goes through CI. `scripts/agent-hooks/guard-convex-cli.sh` enforces this for Claude Code via `.claude/settings.json`; each shell command needs its own unset prefix, including commands within a multiline call. If `.env.local` stops pointing at `127.0.0.1`, restore it with `repairLocalConvexSelection` in `scripts/lib/conductor-workspace.mjs`.

## Product and data boundaries

The filename fixes visibility; server authorization fixes readership. Front matter cannot grant access. `convex/markdownDocuments.ts` and `convex/lib/markdownDocument.ts` own storage, YAML parsing, size limits, and revision checks. Agent-authored company prose is not rejected by keyword blacklists; policy/company boundaries are tool guidance, while authorization, revisions and document validation remain enforced. The inline editor is `components/ui/markdown-editor.tsx`; source and rich editors live beside it. Opening or switching views does not write. Issued snapshots remain immutable; active packet links show saved `public.md` and currently released files. Regeneration rotates a link, while content edits do not.

Operator edits and document imports prioritize `update_client_business_profile` for actual company fields, with version checks and exact approval; `update_client_wiki` is for supplementary notes. Operator Profile uses shared folder tabs for account, business, addresses, related entities, revenue, locations and tech stack; Markdown stays in a Notes card with its own controls. Organizations retain identity, research state, and operational access fields. Policy identity, address, and operations come from policy evidence and policy-specific overrides, never company prose. Do not infer subsidiaries from additional named insureds. `convex/companyResearch.ts` and `convex/actions/companyResearch.ts` own automatic public research on creation and identity edits. Logo import runs for client organizations with a website and no logo. `convex/websiteTech.ts` and `convex/actions/websiteTech.ts` own a best-effort tech-stack scan keyed by website hostname (`websiteTechProfiles`), queued when a client website is set or an intake applicant moves past the website question. It combines deterministic header/HTML/DNS signatures (`convex/lib/websiteTechSignatures.ts`) with a cl-router durable `browse` job (`clRouterBrowse`): a sandbox browser agent with startup-only Browserbase fallback that explores the company's own site and returns visited page text, contacted network hosts, checkout redirects and quoted findings. Each run gets a test identity on `research.spot.insure` (Resend send/receive; random conquistador first name, random unstored password) and a 30-minute capability URL (`/research-inbox`, `convex/researchInbox.ts`) so the agent can sign up, read verification mail and reach billing or checkout; it never enters payment details. Inbound research-domain mail is stored only for live run addresses and never reaches agent or operator email routing. Findings are kept only when their quote is on a visited page and a Jev composite (`convex/lib/jevComposite.ts`, TypeSafe composite scoring over atomic Nouls with code-side weights) confirms the company itself uses the vendor; a second composite scores evidenced candidates for payment processor, hosting provider and data region over page-stated and technical paths. Every stage is optional; failures only mark the scan row and never gate any workflow. The Profile Tech stack tab edits operator-owned `details.techStack` lists (payment processors, hosting providers, customer data countries); each finished scan adds its findings once and never overwrites saved values. Research explicitly selects the nine account, inbox, CAPTCHA, site-page, overlay and payment-observation skills; account deletion is excluded. Up to 40 compact skill outcomes are validated, redacted and stored in `websiteTechProfiles.browse.skills` and returned by operator tools; older records may omit them. Each reports name, version, observed status, summary and step count. Procedure success is not vendor evidence; the existing grounding checks still decide findings.

It reuses each client's company research lease and status, so `get_research_status` and `get_organization` include research reflect it; clients already queued or running are skipped. An answer is kept only with high or medium confidence, a grounded excerpt (Exa citations are read with a bounded retrieval) and Jev `same_company` and `supports` verification (`convex/lib/publicResearchVerification.ts`, shared with procurement information research); others become `unresolvedFields`. Verified answers are stored through `companyResearch.complete` as cited facts (`profile`, `operations`, `scale` sections) that supersede only the same field's earlier fact, reconciled into the company Markdown; `intakeBusinessProfile` is never written. A failed batch fails each claimed client's research without retry under a short Spot code (`research_unavailable`, `research_failed`, `research_entity_failed`, `verification_failed`, `verification_timeout`); a lost action is recovered by the company research lease watchdog, which retries through single-client research.

Request file visibility for clients and providers is independent. New request uploads default to provider-attached; explicit provider hiding remains enforced. ## Convex section extraction and search

Policy and proposal extraction run in Convex. `convex/lib/pdfText.ts` and `convex/lib/pdfSourceSpans.ts` extract pdf.js text, lines, and positioned spans. `convex/lib/policySectioning.ts` groups pages by printed form number and Jev decisions, then slices each section's original PDF. `convex/lib/sectionExtraction/` runs one durable router job per section; on policy PDFs with usable declaration text, `declarationsFastPass.ts` calls fixed cl-router `/v1/extract` (Cloudflare Clairic) for a cited preview and context before the declarations LLM finishes. The plan-bound `declarations_fast_pass` artifact releases the other sections early; non-null grounded fast-pass scalars overlay the LLM result while its structures remain intact. Scanned/empty-text policies and proposals retain declarations-first ordering. `convex/lib/citationResolver.ts` resolves page-and-quote citations to evidence spans. Pages without a text layer receive cited model-transcription spans. `convex/lib/extractionPromotion.ts` gates final promotion on a complete `convex-sections-v1` manifest and grounded evidence. `promoteCompletedExtractionInternal` is the sole final writer; operator overrides survive extraction. The operator policy page has a Sections tab, and `lib/extraction-state.ts` owns shared status presentation. See `docs/architecture/convex-section-extraction.md`.

The former Railway extraction worker, LiteParse/Poppler/OCR, preview queue, `source-tree-v2`, and legacy policy support are removed. The cl-sdk extraction engine is unused and marked deprecated in cl-sdk. Spot still uses its schemas, taxonomy, source-tree helpers, PDF form filling, and prompts. There are no `documentChunks` writes or chunk embeddings. Agent policy retrieval uses Convex full-text search and Jev relevance ranking in `convex/lib/policySearch.ts` and `convex/lib/policyLookup.ts`. `convex/actions/reextractLegacyPolicies.ts` provides a bounded migration action and defaults to dry-run.

## AI and agent execution

- All model generation, decisions, embedding, transcription, and credentialed retrieval go through `CL_ROUTER_URL` and `CL_ROUTER_SECRET`; Spot holds no provider credentials. `convex/lib/clRouterClient.ts` and `convex/lib/clRouterPrimitive.ts` own the transport and task mapping. Router failures fail closed. Rich asset and serialized request limits remain enforced. `convex/routerJobs.ts`, `convex/lib/routerJobClient.ts`, and `convex/actions/routerJobs.ts` own durable jobs, private payloads, scoped assets, callback capabilities, cancellation, and reconnection. Unknown outcomes never replay an inference step. Results up to 64 KiB stay on the job row, and requests up to 512 KiB are written beside it by `prepare`, instead of storage. See `docs/architecture/router-jobs.md`.
- `clRouterDecide` provides Jev Choice/Noul/Score decisions and, through cl-router's images mode, image inputs and Box localization. `convex/lib/pdfPageImages.ts` renders PDF pages for Jev and `convex/lib/jevImages.ts` stages images and locates text on a page (presence Noul plus zoomed Box). `convex/lib/pdfFormFill.ts` fills operator PDF forms for `fill_pdf_form`, and every filled copy is flat. A fillable PDF's fields are flattened as they look blank (checkbox squares drawn from their border colour) and its widgets become known blanks, numbered in reading order: one vision generation reads the pages with each blank outlined and tagged by id, plus the printed words left of, above and (for checkboxes) right of each blank from the text layer (`extractPdfText` `includeItems`), and labels and fills each id, since field names are often meaningless. Other forms get one vision generation that lists every blank and checkbox option with values, then `locateOnPdfPage` per field (a small worker pool; Jev rejects requests that repeat a page image across many questions). `pdfFormFillRuns` holds a fill in progress; the PDF panel shows it live to every operator viewing the form (reading, then each placed field) and moves them to the filled copy when it finishes, and the conversation opens the form while its agent fills it. `pdfFormFills` keeps the original, the current field records (`convex/lib/pdfFormFields.ts`) and filing; `pdfFormFillVersions` holds each saved copy. Refilling the same original for the same client, request and provider adds a version instead of a copy. Each version is a hidden client file (the previous one is archived) and, on a procurement request, one hidden provider-outreach file item repointed to the latest (`convex/pdfFormFill.ts`). Filled forms are edited through the agent, not in the panel: `edit_pdf_form` changes values by reported label (often from a screenshot follow-up), renders the next version from the original with `renderPdfFormFields` and files it. `components/ui/pdf-form-actions.tsx` offers Fill form on a blank PDF (starts the `fill_pdf_form` intent) and Edit with Spot on a filled one (a new chat with the PDF as context). The panel pushes a `pdf_document` page context (`convex/lib/pdfFormSource.ts` source IDs, including provider default application forms) when the open PDF has a known source; `pdfFormFill.getForDocument` reports whether it is filling, filled or fillable. Image and Box answers are experimental: they never solely gate irreversible writes and failures fall back to text. Decompose questions into atomic, self-contained Nouls over structured state and keep deterministic rules in code. `convex/lib/jevThreshold.ts` centralizes the confidence rule: proceed only when the selected choice reaches the threshold, 0.7 by default and set with the Convex env var `JEV_PROCEED_THRESHOLD` (0.5–0.99, read per call). Intake decision bands use that threshold for suggestions, independent `JEV_PREFILL_THRESHOLD` (default 0.8) for answer writes and `JEV_OMISSION_THRESHOLD` (default 0.9) for hiding questions. Uncertain results retain applicant input. Prompt screening treats content as safe only when the safe choice reaches that threshold. Jev selects among known candidates for intake, page sections, team inbox quoted-history starts, carrier identity, coverage scoping, grounding fallback, organization names, mailbox automation, and other classifications; generation supplies prose and extracted values. `convex/lib/agentToolSelection.ts` owns shared family selection, availability, required families, intent shortcuts, fallback, expansion schemas, guidance, and telemetry. `convex/lib/clientAgentPrompt.ts` selects client families, answer depth, and Slack reaction in one Jev call, then uses AI SDK `prepareStep` for active tools and guidance; `expand_tools` loads families on the next step of the same turn. Used families stay active, and selection cannot grant tools excluded by surface or authorization. `convex/lib/channelControls.ts` classifies email, Slack, and certificate endorsement intents. Email send authorization is stored on the message as `emailSendAuthorization`.
- Certificate endorsement eligibility uses stored, cited insured/class candidates and Jev endorsement decisions; uncertainty or router failure holds issuance. Carrier identity selects retrieved sites and name relationships with Jev, then retains deterministic metadata naming and source grounding. Compliance manual review asks Jev atomic per-policy questions (insured, coverage, provisions) and derives status in code from deterministic limit and date checks. Company research starts deterministically, verifies identity with per-candidate Jev checks and a tie-break choice only when several sites pass, and retains generation only for profile prose. Proposal review generates section findings; code derives the overall conclusion.
- Research, requirement extraction, supplementary extraction, proposal review, and title generation carry task kinds and parent/job traces. Research retrieval traces are stored in Spot's durable job metadata because the router retrieval request contract does not accept trace fields. `convex/actions/threadTitle.ts` owns short (≤4-word) title generation for client threads, including MCP, and every operator thread (`generateOperatorTitle`; Slack keeps its prefix). The operator dock history lists Recent chats (MCP requests included) with a "Show archived" link at the bottom (`operatorAgent.listThreads` `view`).
- Operator context compaction estimates full system/tool/message input and summarizes older complete exchanges before the model limit (`convex/lib/operatorContextCompaction.ts`, `operatorContextCompactionRunner.ts`, `convex/operatorContext.ts`). Core `compact_context` requests it proactively; exact reference metadata, recent call/result pairs and continuation recovery/retry state survive. Summary failures fall back to deterministic notes, and an original history that still fits the hard input limit remains usable when notes do not fit. Server approval records remain authoritative. `operatorThreadContextStates`, `convex/operatorAgentHistory.ts` and `convex/actions/compactOperatorThreadHistory.ts` own rolling summaries of aged-out operator turns, reusing tenant history helpers and the routed `summary` task without changing tenant behavior. See `docs/architecture/operator-context-compaction.md`.
- Operator goal planning uses `convex/lib/operatorPlanning.ts` and `operatorRunPlan.ts`: one Jev request with five risk Nouls (changes records, changes several records, a change depends on an earlier change, sends outside the company, target needs a search) and a target-count Score; `planningLevelFromAnswers` composes them into a graded `level`: `full` (separate durable planner call at default reasoning effort with one-line tool summaries, before business tools; a truncated or invalid plan downgrades the run to `checklist` with `plannerFallback`, while router failures keep their retry path) for multi-record or chained changes, five or more targets, or an external send alongside changes; `checklist` (no extra call, a system prompt block asking the first reasoning to list targets and steps) for several targets, a change or send to a target that must be found first, or any uncertain answer; `none` otherwise. Operators can force `full` with the composer's Plan toggle (`sendMessage` `planMode`, `operatorAgentRuns.planRequested`), which skips Jev. `planningAssessment` stores level, answers, source and requestId; legacy rows with only `required` read through `operatorPlanningLevel`. `operatorPlanningCalibration.listRecentRunsInternal` lists recent runs' assessments beside outcomes for threshold checks. The run and assistant message retain any plan. `operatorToolRecovery.ts` bounds correctable no-write failures to three subsequent model iterations, persists recovery with continuation, and excludes exhausted tools; it never authorizes unknown writes or bypasses approvals. `operatorAgentToolFailure.ts` owns structured codes and guidance; `NoWriteInputError` carries known pre-write failures across Convex boundaries. Tool schemas still validate before dispatch. Search/list tools disclose scan and result bounds; failed or incomplete searches cannot prove absence.
- Operator tool families use the shared selector with existing intent shortcuts and all-family durable resume behavior, and expand with `expand_tools` on the next step. Confident families always load and uncertain-band families (≥0.5) load under a tool-token budget (`composeAgentToolFamilies`); team inbox reads are `team_inbox`, sending is `outbound_email`, operator chat history is `operator_conversations`, and retired names map forward via `normalizeOperatorToolFamilies`. `expand_tools` answers `already_available` with callable tool names instead of loading nothing. `search_team_inbox` runs as an action: `convex/lib/teamInboxTargets.ts` flags exact subject matches as targets in code and asks Jev (one batched decision, top 10 candidates) only when a named target has no exact match; results carry `subjectMatch`, `matchedIn`, `likelyTarget` and top-level `targets`. The first step of a run withholds `expand_tools` when a domain family is already loaded (`withholdExpandToolsOnFirstStep`); a resumed first step that lost its stored families keeps it so replayed responses stay valid. Families are selected once per run and kept in `checkpoint.families`; later iterations reuse them plus required families. Follow-up turns reconstruct used/expanded families from the last eight assistant message audits within 24 hours. `expand_tools` accepts family/tool names through `families`, `family`, `tool_families` or `tools`; dependency lookups are declared in `agentToolSelection.ts`. `operatorToolOutput.ts` bounds model-facing results/history and strips raw tool envelopes before final persistence; provisional operator reply text streams through the same sanitizer in `routerJobs.progress`. `operatorMcpReadCalls.ts` records direct MCP reads on per-call runs/messages without patching the shared conversation, retaining cursor/draft/attachment continuity. The `DURABLE RUN CHECKPOINT` prompt text is injected only when no stored continuation exists, and the prompt carries the operator's name and email for signing drafts. One runner action executes consecutive model steps for up to four minutes, checkpointing continuation and iteration after each step (`continueRunInternal` `inline`; continuations up to 512 KiB are written as an `operatorRunContinuations` document by that mutation, larger ones as a blob stored first) and handing off to a scheduled run at confirmations, cancellation, router retries, yields or the budget. Durable agent calls wait in place up to 45s for their router job row (`inlineWaitMs`, polling every 100ms for the first 3s), then yield; a finished router job wakes its queued operator run immediately (`routerJobs.finish`), with a 10s fallback poll. Each runner segment records metadata-only timing (`convex/lib/operatorRunTiming.ts`: self-time phases, model calls split into router submit/wait/read, SDK and telemetry, with the model's finish reason when reported, per-tool queue/execute/bookkeeping) into `operatorRunTimings` through the mutation that ends the segment, never a write per phase; `get_operator_run` returns it as `timing`. A reply that writes a tool call as text (`convex/lib/leakedToolCallText.ts`) is never finalized or streamed: the run is retried up to twice with a corrective notice, then answers with the stripped text, and history replay strips such spans. The active role, impersonation, configured integrations, exact target authorization, and approval are rechecked at execution. `convex/lib/operatorAgentToolRegistry.ts` owns the registry. The global **Approve all** switch on `/operator/settings` is off by default and automatically satisfies new exact approvals only when enabled; existing pending approvals still require a decision. Tenant approvals are separate. The same runner serves operator web, email, Slack, iMessage, and MCP channels.
- Operator command email uses the shared `agent@team.spot.insure` Resend inbox and private operator conversations keyed by Resend thread ID. `convex/operatorEmail.ts` and `convex/actions/handleInboundOperatorEmail.ts` verify aligned full-body DKIM from original Receiving MIME before resolving an active operator. Only unavailable raw MIME permits a durable `emailReadOnly` run; every tool selection/execution boundary excludes writes, sends, saved drafts and external MCP calls. Explicit authentication failures reject. Responses target the canonical operator login, never unverified Reply-To/CC. Quoted history is separate from current instructions, and email cannot approve exact writes. Legacy `operator(+thread)@agent.spot.insure` remains authenticated. Operator identity matches normalized localparts across the exact `toolsforenlightenment.org`, `spot.insure`, and `claritylabs.inc` domains after mailbox verification.
- Processing web messages carry bounded live `activity` (tool name, call id, status), recorded by the runners and optional router `toolCalls` progress metadata. Requested calls are not yet running, and returned calls do not imply business success. Show thinking defaults to visible while preserving explicit opt-outs. `convex/lib/messageActivity.ts` owns the state contract.
- The shared chat component architecture is in `components/chat/`. Bounded message activity retains observed preparation, tool/model selection, and tool lifecycle stages through completion or failure. Router stages arrive through the authenticated progress capability; never expose decision inputs, raw reasoning, or provider error bodies in the chat trace. `lib/chat-presentation.ts`, `lib/chat-presentation-catalog.ts`, `convex/lib/chatPresentationCandidates.ts`, `convex/lib/chatPresentationComposer.ts`, and `convex/chatPresentations.ts` own grounded presentations and current-reference authorization. Composition cannot execute business tools. Unsent email drafts become an `email_draft` reference (authorized only for the owning operator or client thread) with metadata-only evidence (no body) and grounded send/shorten/attach/cancel follow-ups; the draft card remains the only rendering of the email.
- The browser extension in `extensions/spot/` hosts the client agent at `/extension`, reusing chat, history, attachments and artifact cards. `config/browser-extension.json` and `lib/browser-extension.ts` own the exact-origin, bounded page-capture bridge. Capture requires an explicit browser action and stages a removable attachment; it never submits a message or executes tools. Keep authentication and business authorization in the app/backend, with no extension token relay. See `docs/architecture/browser-extension.md`.

## Insurance request intake

Quote submissions with current electronic-signature consent ensure one client-owned representation grant: `organizations.intakeAuthorizationId` points to the immutable `requestIntakeAuthorizations` record (legacy table name; the source request/hash are provenance only). `convex/intakeAuthorizations.ts` reuses that grant across new requests and resubmissions; `convex/actions/intakeAuthorization.ts` and `convex/lib/intakeAuthorizationPdf.ts` render one branded PDF. Its `clientFileId` appears in Clients → client → Files → Shared; request files and Spot Packets reference the same client file through the existing revocable `/packet-file` capability. Pending publication links requests in bounded batches; deleting the source request does not remove the client grant. Lazy adoption preserves existing signed bytes, archives older generated forms and retains release/removal choices; no consent is backfilled. The form records exact consent, signer, timestamps, versioned terms URL and original submitted-content hash. Its signature box displays a cursive name placeholder; never infer handwriting. Initial automated broker emails keep their empty attachment list. Savings reviews are excluded. See `docs/architecture/insurance-intake.md`.

`convex/requestIntake.ts` owns user-owned drafts, revision saves, upload staging, and submission before optional email confirmation. `procurementRequests.clientOrgId` is optional before company attachment; fulfillment and shared packets require a company. A new self-serve applicant gets a limited client organization and admin membership as soon as they move past the legal-name question; `organizations.intakeDraftRequestId` marks it until submission so name/website edits keep it in sync, and switching to a saved company soft-deletes it. Operator Clients lists every client in one table with All/Active/Limited/Archived/Onboarding filters. Limited clients with an unsubmitted intake draft display as Onboarding instead of Limited, and applicants who have not named a company yet appear as Onboarding rows (`operator.listUnlinkedApplications`). Restricted unverified users can access only their own drafts and uploads. `/api/intake` and `requestHandoffs` provide an expiring, hashed landing handoff; existing emails require OTP before access and new accounts can submit before verifying, then confirm email from the submitted application banner. `components/insurance-intake/` owns focused conditional questions, the shared intake frame, local recovery, and the editable post-submission application overview. Website entry schedules request-owned prefill through `convex/actions/intakeCompanyResearch.ts`, reading the applicant-provided website directly without a company-name identity gate, creating an organization, or overriding user answers. Requirement uploads reuse `convex/actions/complianceRequirements.ts` through one-shot `convex/actions/intakeRequirementPrefill.ts` and request-owned suggestions; failures stay server-only and suggestions never overwrite entered answers. Coverage lines own their limits, additional requests, and bounded property/vehicle scope; company-level lines bypass item scope. Submitted edits preserve the original snapshot. Submission preserves the original snapshot and writes the canonical typed `intakeSubmittedApplication`; admin submissions promote an allowlisted `intakeBusinessProfile`. Draft saves never publish facts. Markdown is a sharing/export projection, with authored notes and control markers retained. The manual intake readiness checklist and lifecycle gate are removed; procurement uses its ordinary lifecycle controls. Application and company views render typed facts through shared intake row-card components. Shared packet exports generate Markdown tables from the accepted application, hiding control comments only in presentation and retaining them in source. `convex/intakeSlack.ts` owns the request-scoped Slack outbox: one #submissions thread, untagged step progress, and @here only on submitted/resubmitted events, delivered through the Convex Slack Web API transport (`convex/lib/slackWebApi.ts`). ## Post-deploy operator checklist for this extraction release

After the release deploys to an approved target:

1. Decommission the Railway `spot-extraction-worker` service.
2. Remove `EXTRACTION_WORKER_*` and `LITEPARSE_*` variables from Convex deployments.
3. Run `npx convex run actions/reextractLegacyPolicies:run '{"dryRun":true}'`, then repeat with `{"dryRun":false}` after review. Page with the returned cursor until `isDone`. Run `npx convex run modelSettings:stripRetiredRoutesInternal '{}'` and `npx convex run modelSettings:clearOperatorModelOverridesInternal '{}'`, paging each returned `continueCursor` until `isDone`. Select the intended deployment explicitly and use `--prod` only for an approved production run.
4. Drop schema tables and fields marked `// Deprecated` after data cleanup and verification on every deployed target.
5. Set `FLAGS_SECRET` and `WEBMCP_ENABLED` where WebMCP should be available.
6. Verify client-family behavior through the browser workflow QA ledger; the opt-in unit eval suite was retired in the October 16 test reduction.

Generation routes through cl-router by default, including every operator step. `mapSpotCallToClRouterPrimitive` maps generation to `text` or `reasoning`; Spot sends no explicit `requirements` because cl-router infers capabilities and context size from the payload. Its provider introduction, provider nudge, signature template, provider signature note, writing rules and provider rules are `DEFAULT_EMAIL_PROMPTS`, editable without a deploy in `/operator/settings?section=email` (`components/settings/email-prompt-settings.tsx`, `convex/emailPrompts.ts`, table `emailPrompts`: `userId` null is shared, an operator's own row may set only `signature` (replaces the shared one) and `writing_rules` (appended as their preferences)). `loadEmailPrompts` (`convex/lib/emailPrompts.ts`) resolves them; `outreachSenderIdentity`/`operatorSenderIdentity` and `providerOutreach.claimStepInternal` carry the sender's `prompts`, so every signature, cold introduction (including the `{{introduction}}` merge value) and nudge uses them. Provider outreach, inbox auto-drafts (`convex/actions/teamReplySuggestions.ts`), provider draft tailoring and the operator agent (system prompt block when the outbound_email, procurement or team_inbox family is loaded, with the operator's preferences) include the configured rules; the client agent keeps the fixed `EMAIL_SKILL_TONE`. Saved drafts keep the text they were composed with. `buildOperatorSignature` appends the provider signature note below the sender signature only when the To recipient is a provider (`toProvider`); clients never get it. `convex/lib/providerRecipients.ts` resolves addresses to providers; operator compose and every operator inbox send (claim and final pre-send check in `convex/emailDeliveryAttempts.ts`) refuse Do Not Contact recipients, and auto-drafts skip them.
