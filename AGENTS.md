# AGENTS.md

Guidance for any coding agent working in this repository: Codex, Claude Code, Cursor, or similar tools.

## Current procurement and ownership boundary

The current implementation supersedes older ownership descriptions later in
this file: procurement projects use the request/proposal/broker-profile modules
listed below; proposals and market activity are operator-private; client
Requests use an allowlisted DTO; broker members have profile/team-only access;
and policy mutations plus procurement staff writes are operator-only. Client
organizations are standalone and do not inherit broker branding, agent
channels, policies, or access. Automated policy delivery is retired (its
legacy tables remain only for the explicitly gated purge/narrowing migration).
The tenant MCP catalog contains no broker portfolio or procurement proposal
tools. When an older paragraph conflicts with this boundary, follow the active
Convex/UI contracts and the staged migration commands in this file.

## Current router-owned AI credential boundary

The current implementation also supersedes older model-routing descriptions
later in this file. Spot Convex and every Spot worker contain no AI, Parallel,
Exa, gateway, or Moonshot credentials and perform no direct provider execution.
Every generation, stream step, structured output, embedding, voice
transcription, extraction callback, and credentialed web retrieval uses
`CL_ROUTER_URL` plus `CL_ROUTER_SECRET`; tenant identity remains `glass`.
Provider availability comes from the authenticated router capabilities action,
while static route edits validate only model/task capabilities. Settings and
worker claim snapshots never contain `providerKeys`. The explicitly selected
`operator_agent` route is sent to cl-router as a pin and remains stable across
the Spot-owned business-tool loop. Router failures fail closed in Spot without
consumer break-glass, alternate transport, or tool replay after visible output.
Large PDFs, images, and audio use signed Spot-owned asset references: emitted
rich binary parts are limited to 12 MiB per asset, 16 MiB decoded in aggregate,
and eight assets after parsing/selection; every caller
also enforces Convex's stricter 4 MiB serialized UTF-8 JSON request ceiling.
Generated worker images that cannot stay inline are staged in a short-lived,
lease/org-bound Spot ledger and deleted after use or bounded expiry cleanup.
`brokerModelSettings.providerKeys` remains optional only for the explicit
audit/cleanup migration and must not be read by runtime code. When an older
paragraph conflicts with this boundary, follow this boundary and the active
router client, settings, migration, and worker contracts.

Router rollout acceptance uses only the bounded internal fixtures documented in
`docs/deployment/environments.md`. `convex/operationalRouterSmoke.ts` owns the
random marker ledger and `convex/actions/operationalRouterSmoke.ts` owns the
deploy-key-only generation/object/tool/embedding/retrieval/transcription/PDF
action. It accepts only bounded M4A bytes and returns booleans, counts, and
request IDs. The extraction-worker transport proof uses the separate
never-queued active-lease fixture in `convex/workerRouterTransportSmoke.ts`, the
worker-authenticated actions in `convex/actions/workerRouterTransportSmoke.ts`,
and `/app/dist/routerTransportSmoke.js`; it must never call global claim,
completion, enrichment, or delivery paths. Both fixtures have marker-validated
cleanup plus scheduled bounded retry. Do not broaden either API with caller
selected organizations, users, URLs, models, storage IDs, or deletion targets.

## Workflow

- After major architecture or data-flow changes, update `AGENTS.md`.
- Keep `AGENT_TOOLS.md` synchronized with every model-callable operator tool, tenant/client agent tool, internal agent-subagent tool, operator MCP addition, and tenant MCP tool. Any tool add/remove/rename or material availability, capability, effect, role, confirmation, execution-boundary, or MCP-access change must update that inventory in the same change.
- Prefer documenting current behavior over planned behavior.
- Treat the Convex worktree as potentially dirty. Do not revert unrelated user changes.
- Use Node 24.x everywhere in this repository. `.nvmrc`, `.node-version`, package `engines`, Node-based Dockerfiles, and `convex.json` are the runtime contract; Conductor bootstraps Homebrew `node@24` and prepends it to `PATH`.
- Name Convex indexes, search indexes, and vector indexes with one or two plain-English words, such as `organization_status` or `private_history`. Do not use `by_`, `and`, or field-by-field index names; the indexed field array is the source of truth.
- Use `dayjs` for date parsing, formatting, comparisons, and timestamps in new or touched code instead of raw `Date.now()`, `Date.parse()`, or `new Date(...)`.
- Use the shared `PillButton` primitive for pill-shaped action buttons across app surfaces, including primary, secondary, destructive, footer, and app-shell actions. Every destructive action button uses `variant="destructive"`; icon-only destructive actions add `iconOnly` and a nonempty `label` instead of switching to `Button`, a raw button, or custom red classes. Internal `PillButton` hrefs use Next client navigation with full prefetch by default; external URLs, protocol links, and downloads retain native anchor behavior. When an action needs native link or download behavior, render `PillButton` with `href`, `target`, `rel`, or `download` instead of hand-rolling rounded anchor/button classes. Raw `<button>` elements are for non-pill structural controls such as row targets, tabs, menu triggers, and non-destructive navigation controls.
- Operator portal pages use the app-shell breadcrumb as their page identity. Do not repeat the route title or add a page subtitle in the content area; put persistent status tags in the overview or active-tab body and route facts in the active tab.
- Operator portal route tabs use the shared pill treatment (`TabsList variant="pill"`). Content beneath an active tab does not repeat the tab name in a panel header or add an explanatory card subtitle. Prefer `OperationalLabelValueList` and `OperationalLabelValueRow` over asymmetric multi-column detail layouts; when short facts and long prose coexist, place compact value pairs in a top card and long-form rows in a separate card below.
- Follow `docs/design/interface-style.md` for browser colors, border strength, spacing, surface choice, card use, shape, elevation, and responsive layout. Follow `docs/design/typography.md` for browser text roles.
- All tables use rows for readable data and keyboard-accessible sidebar navigation. Do not put action buttons, action menus, edit controls, or dropzones in table rows. Put editing and upload controls in the sidebar and all record actions in its footer. Keep sidebar sections quiet: omit headings that merely repeat what filenames or controls already identify. Upload and extraction progress belongs in toasts, not notes embedded in or beneath dropzones. Broker/client selectors show the organization's `OrgBrandIcon` beside both options and the selected name.
- For iterative visible cloud-Chrome workflow QA, follow `.agents/skills/cl-workflow-qa/SKILL.md` and maintain the scripts and coverage ledger in `docs/testing/workflow-qa.md`; route loads alone do not establish passed workflow coverage.
- Follow `docs/testing/README.md` when deciding whether a change needs automated coverage. Prefer a small number of durable, risk-focused tests over broad implementation or UI coverage.

Each policy's source spans and nodes are read through bounded action-side query pages before one compact fingerprint-guarded decision mutation; write mutations atomically persist the per-policy result so a partial page retry cannot lose committed counts or samples.

Only after every audit page is reviewed on the approved target, run `migrations:runCarrierIdentityBackfill`, monitor the migrations component, and read write outcomes with `npx convex run carrierIdentityBackfill:reportInternal`. The write migration schedules one evidence-paging action per eligible policy with bounded automatic retries, and the report must reach `pending: 0`; if an interrupted action remains pending, requeue a bounded page with `npx convex run carrierIdentityBackfill:retryPending '{"limit":25}'` and continue from its returned cursor. Both audit and write paths read source spans and nodes through bounded query pages outside migration transactions.

After review, run `migrations:runSlackInboundEventMentionsSpotBackfill`, then require `slack:verifyInboundEventMentionsSpotBackfill` to report `complete: true` before removing the optional legacy field in a later schema-narrowing release.
- `npx convex run migrations:backfillCompanyInformationFactSections '{"dryRun":true}'` — audit the widening-phase cleanup behind the company wiki. After review, run `migrations:runCompanyWikiLegacyPurge`, which routes section-less legacy organization facts to `profile`, clears `companyInformationExtractions.procurementFacts` and `connectedEmailAutomationItems.memoryIds`, and purges the retired `orgMemory` and `procurementMemory` row stores. ## High-Level Architecture (v0.2.0)

Spot is an insurance intelligence platform built on Next.js + Convex. v0.2.0 is focused on post-binding policies, renewals, operator-assisted new-policy procurement, an agentic chat assistant, an agentic inbound email agent, connected-mailbox automation, lightweight per-org knowledge store (`orgWikiSections`), and compliance workflows. The old Applications v2, Client Passport / ACORD 125, the old persisted inbox product, org context documents, and Merge.dev sync backend remain removed.

Core layers:

- Frontend: Next.js 16 App Router, React 19, Tailwind 4, and `@lisse/core` for app-wide continuous-corner geometry
- Backend: Convex queries, mutations, actions, scheduler, file storage, vector search
- Browser sync: `@claritylabs/cl-sync` provides reusable IndexedDB-backed local-first sync primitives. The package is maintained as the sibling public package `../cl-sync`; Spot owns only its app-specific collections and cache policies under `lib/sync/`.
- AI runtime: Vercel AI SDK (`ai`)
- Internal operator agent: `convex/operatorAgent.ts`, `convex/operatorAgentRunner.ts`, and `convex/lib/operatorAgentToolRegistry.ts` own the durable authenticated operator loop, dedicated operator threads/messages/confirmations, typed capability/effect/execution metadata, ownership checks, exact-confirmed writes, and idempotent audit ledger. A portal thread captures its first available page context as immutable origin context and injects that same routing hint into every later run, including turns continued away from the originating page; later page navigation never replaces it. Action-backed tools revalidate the active operator and exact fingerprint at their asynchronous boundary; shared rich client policy, compliance, and file reads execute through `convex/actions/operatorAgentRichTools.ts`, while exact source-backed policy writes still require registry confirmation. `search_organizations` includes legacy client rows and bounded human-name typo tolerance but still returns exact IDs for downstream tools. Exact confirmation summaries resolve persisted target names or titles before reaching a human surface and never expose storage IDs; portal confirmations stay anchored to their prompting message as durable pending, approved, cancelled, expired, superseded, or unavailable timeline artifacts, with `PillButton` controls only while the current operator can act, while Slack uses signed, actor-bound Confirm/Cancel Block Kit controls and removes them after the decision. `search_thread_history` and `read_thread_attachment` recover bounded older operator context and only reopen files already registered to the exact thread. `lookup_address` reuses permanent Mapbox validation, while exact-confirmed `generate_coi` reuses the shared certificate batch generator and registers successful PDFs as protected operator-thread attachments before resuming the same goal. Approved writes resume the same goal; long goals checkpoint bounded tool evidence and reschedule additional segments instead of treating a model step ceiling as completion. `convex/lib/agentAttachmentContext.ts` owns bounded PDF, image, XLSX, CSV/TSV/text, JSON/XML, DOCX, and PPTX model input shared with tenant chat; the portal, Slack, iMessage, and MCP adapters store files before enqueueing the same core turn. Portal files use expiring operator-owned upload intents that are consumed with the message or delete any unreferenced blob after failure/expiry. `convex/lib/operatorMcpToolCatalog.ts` derives one role- and scope-filtered MCP catalog from the registry. `convex/lib/operatorAgentIntentRegistry.ts` is the single versioned owner for operator task launchers: the server resolves applicability from immutable page context, renders the visible opening objective, and records intent ID/version as a structured message artifact before the ordinary governed run begins. The `operator_agent` model route is a required, explicitly saved, image-capable router pin; it is included in key-free router snapshots with router fallback disabled and fails closed when unavailable. The persistent `/operator` right rail and dedicated `/operator/threads/[id]` pages reuse one operator conversation renderer plus the client thread's `ThreadMessageBubble`, `AgentThinkingBubble`, attachment chip, and `ChatInputOverlay` primitives; rail density is a shared overlay variant rather than a second composer. `/operator/threads` is the default operator entry and owns task starters plus the tabular Active/Archived inbox; archive and restore are reversible operator-authorized thread transitions, and new activity automatically returns an archived thread to Active. The operator sidebar shows active cross-channel threads, while the rail's recent-task picker shows only active portal threads whose immutable origin shares the current page scope. Clarity-host Slack DMs/mentions, the separate operator Photon lane, and audience-bound MCP are adapters to this same core. Never route operator records through tenant `threads`/`threadMessages`, accept an unlinked Slack/phone identity, add a generic database escape tool, execute a non-read tool outside the registry confirmation policy, or let attachment content expand authorization.
- Client file dropbox: `convex/clientFiles.ts` owns operator-only upload intents, public mutations, visibility-filtered reads, signed URLs, naming scheduling, and source lifecycle; `convex/lib/clientFiles.ts` owns generated-API-free shared write invariants for UI, operator-agent, and procurement ingestion paths. Same-client policy links, explicit client visibility, expiring upload cleanup, and operator audit events protect miscellaneous client documents. `convex/actions/clientFileNaming.ts` reuses the bounded attachment parser (LiteParse first for PDFs) and the `classification` or `chat_vision` model route to propose an initial name from contents, with the operator hint as untrusted context; a manual rename wins over a late model result. Every active stored client file also schedules the source-owned company-information workflow in `convex/actions/companyInformationExtraction.ts` and `convex/companyInformation.ts`: the shared bounded parser feeds `document_extraction` for readable documents or `chat_vision` for images, high-confidence application/profile values fill the source-backed organization profile first, and remaining durable facts reconcile into `orgWikiSections`. The extraction ledger keeps exact source contributors, retries transient failures without escalating low-cost model routes, rejects stale completions, and removes that source's structured and memory contributions when the file is archived or deleted; restoring a file schedules a fresh extraction. `components/client-files/client-files-workspace.tsx` is shared by the operator client route and the client-only `/files` route. Operators browse Private, Shared, and Archived tabs, and each tab reads its own indexed page of `clientFiles`; only operators may request the archived view. Archiving is reversible from the Archived tab, keeps a file out of every client and agent read, and blocks name/policy/visibility edits until it is restored. PDFs open in the app PDF panel, browser images open in the right panel, and every other format downloads. Shared client-agent lookup/read/attach tools and direct tenant MCP list/get tools may expose only explicitly client-visible active rows within the caller's current readable client scope; operator registry reads may include private active rows after revalidating the active operator. Agent adds file privately and run immediately without a confirmation, agent edits remain registry-backed exact-confirmed writes because they can expose a file to the client, and an add may consume only an attachment already bound to that operator thread, resolved by exact storage ID or that attachment's exact filename. Files are operator-private by default and client/broker reads must remain visibility-filtered. A client may upload a supporting request file through its allowlisted request page; that writes one `clientFiles` artifact with `uploadedBySide: "client"` and one client-visible `procurementFileItems` association, never a legacy request document or activity row.
- Procurement projects: `convex/procurementRequests.ts`, `convex/clientProcurementRequests.ts`, `convex/procurementPacket.ts`, `convex/procurementProposals.ts`, and `convex/brokerProfiles.ts` own requests, the client collaboration boundary, the shared packet document, private proposals, and the supplier network. `convex/lib/procurementCapabilities.ts` is the versioned browser/Spot-agent parity contract; all operator-agent channels and operator MCP inherit the same registry commands. The product boundary is deliberately coarse: the request narrative is client/operator intake; every non-operator packet section is part of one Markdown document visible identically to the client and broker market; operator-only context, market activity, proposals, reviews, and internal files never enter that document. Canonical packet sections remain an internal extraction and review implementation detail and their empty slots are not user-facing requirements. A request carries one intake field, `narrative`, which seeds the packet; everything else about the shared submission belongs in packet sections. Proposal filing is one atomic, replay-safe business command over canonical private `clientFiles` artifacts and never creates an empty shell. Proposals remain operator-private and bind reviews to `packetRevision` plus the extraction fingerprint. The operator workbench exposes Overview, Packet, Market, Files, and Imported email; proposals live with their broker market rows rather than in a separate route, and Overview is a compact decision summary rather than an audit timeline. Packets, outreach, and imported email never enter tenant MCP.
- Procurement email reconciliation: forwarded attachments are canonical private `clientFiles` artifacts. Reconciliation suggests an outreach only for one exact participant/contact match; otherwise the operator must choose one. The web drawer and exact-confirmed Spot-agent command call the same atomic proposal-filing service, preserve `sourceEmailThreadId` in audit metadata, deduplicate artifacts, queue extraction, and converge on replay.
- Broker packet sharing lives at the top of the request's `Market` tab. One request-wide, hashed, expiring, revocable link snapshots the shared packet and request-wide released files for every broker. Creating or replacing it revokes the previous active request-wide link, and the secret is shown only for immediate copying. Outreach-bound files are never included in this shared link. Legacy recipient-scoped link rows remain readable and revocable but cannot be created from the browser or operator agent.
- Agent-led procurement setup may create a standalone client organization without provisioning users through the exact-confirmed `create_client_organization` operator command, then use its returned exact ID for request creation. The browser and agent paths share `operator.createSoloClientInternal`; exact-name duplicates and active impersonation fail closed.
- Tenant OAuth MCP: the typed `MCP_TOOLS` catalog in `convex/http.ts` is the single owner of each tenant tool's effect and MCP annotations. The dispatcher derives the write-scope gate from that same entry before invoking a handler. `ask_spot` and `ask_glass` also pass the token's write capability into the nested client-agent and mailbox-coordinator catalogs, so a read-only token cannot select a write/import/save/invite tool through an otherwise read-classified chat call.
- Extraction, query agent, prompts, and canonical ACORD policy taxonomy: `@claritylabs/cl-sdk` 4.6.0 source-tree contract. Legacy v2-style `sourceSpans` remain read-compatible through the same canonical `sourceNodes` / `operationalProfile` storage shape.
- AI providers: cl-router owns every provider client, credential, candidate, and failover decision. Spot submits configured/static routes and explicit operator pins through the authenticated router only; embeddings remain 1536-dimensional for the current Convex indexes.
- PDF parsing: bound policy and renewal extraction use parser-neutral source spans. Spot builds/stores `sourceSpans` as the smallest PDF evidence layer, `sourceNodes` as the canonical hierarchy/search layer, and `operationalProfile` as a source-backed policy fact projection for policy lists, COIs, compliance, and comparisons. When the Railway extraction worker is available, Spot first preprocesses PDFs with LiteParse, building page/row/cell spans from positioned text, preserving bounding boxes for exact source citation highlights, and capturing bounded page screenshots for multimodal page-scoped model calls. Full extraction, provisional extraction, and authenticated HTTP conversions all share one serialized native LiteParse lane while the surrounding job/model work remains concurrent; bounded priority bursts preserve latency without starving full parses. The worker starts with OCR disabled and retries the same document once with bundled English Tesseract data only when that pass produces no usable spans, so image-only PDFs still enter the source-backed SDK contract without imposing OCR on text PDFs. The worker then uses Poppler page text only as a bounded supplement when it exposes visible filled-form text omitted by LiteParse. If LiteParse fails or times out, Spot falls back directly to local PDF.js source spans without retrying the same synchronous conversion, plus the same supplemental visible-text check. LiteParse and Poppler are hosted inside `extraction-worker/`, not as separate services, feature flags, or callback interception layers.
- Provisional extraction: new policy uploads enqueue a lightweight `policyExtractionPreviewQueue` job alongside the full extraction run. The worker uses LiteParse/PDF.js text, any selected Poppler visible-text supplements, and the `extraction_preview` model route to populate a bounded allowlist of policy fields on the existing policy row with `extractionDataStage: "preview"`, including the source-stated carrier product/plan through the `programName` compatibility projection; the full extraction authoritatively replaces or clears both `productIdentity` and `programName` from final source evidence before setting `extractionDataStage: "final"`. Agents, MCP policy summaries, and live compliance views can read preview policies. Duplicate detection, COI generation, source-backed fact confirmation, policy changes, endorsements, and scheduled compliance notifications remain final-only.
- Email: outbound + inbound via Resend, plus user-connected generic IMAP mailboxes for live agent search/read and opt-in proactive policy, requirement, and company-context automation. The proactive scanner persists only cursor/outcome metadata and imports selected first-class artifacts; raw mailbox bodies remain remote. All outbound Resend calls go through `convex/lib/resend.ts` (`sendResendEmail`). The primary signed-in web app is `app.spot.insure` for both broker and client users; broker/client landing is role-based after sign-in. `spot.claritylabs.inc` is the legacy browser host and redirects to `app.spot.insure`. `auth.spot.insure` is an auth/invite email sender domain rather than a separate web app host. Agent mail defaults to `spot.insure`, notification mail defaults to `notifications.spot.insure`, and auth/invite mail defaults to `auth.spot.insure`; legacy inbound agent addresses at `spot.claritylabs.inc` and `dev.claritylabs.inc` remain recognized. Inbound webhook at `POST /resend-inbound`. Reissued links revoke the prior link for that draft and channel, edited, cancelled, sent, stale, or expired drafts fail closed, the nightly sweep deletes expired rows, and personal iMessage history deletion deletes links for the removed thread before preserving its detached business records.

Transactional mail is Spot-branded; the shell owns light/dark color-scheme metadata, `prefers-color-scheme` rules, Outlook `data-ogsc`/`data-ogsb` overrides, and legacy `bgcolor` fallbacks. Do not create a standalone email document or declare a light-only scheme. Agent-authored free-form reply HTML remains outside this fixed-template contract.
- Procurement boundary: Spot owns operator-assisted client procurement requests, broker outreach/application requirements, requested documents, and the final quote/decision needed to bind a resulting policy. It does not restore the former client-facing Applications v2 funnel, broad CRM sales pipeline, carrier-submission automation, or a general unbound quote library. Keep procurement client-scoped and operator-managed through the dedicated request records and client Dropbox links rather than recreating removed application tables or `/applications` routes.

They own their policies, agent channels, compliance, and procurement requests; Spot has no broker-owned client portfolio, broker white-labeling, automated policy delivery, or broker/client assignment workflow. Brokers are network suppliers with profile/team access only. Legacy program-admin rows and delivery tables remain only for the explicitly gated migration purge.

Multi-value business fields such as aliases, labels, categories, or tags should be stored and edited as lists, not comma-delimited text.

## Current Model Routing

Convex cl-router calls keep small generation inputs inline, send HTTPS files and images as bounded asset references, stage transcription audio in temporary Convex storage for the JSON transcription contract, and chunk embeddings so each response contains at most 200,000 numeric values. The extraction worker sends the original storage-backed PDF URL while retaining inline page images.

Route definitions, capability budgets, provider normalization, static challenger/fallback candidates, and rating thresholds come from exact-pinned `@claritylabs/cl-router-policy`. [convex/lib/modelCatalog.ts](convex/lib/modelCatalog.ts) layers Spot-only UI labels, selectable model catalogs, and route groups over that package. The extraction worker imports the same package directly, so every caller shares one versioned policy vocabulary while cl-router owns provider execution and credential availability. cl-router has no active offline benchmark or quality-bar path: explicit human ratings use a 5-up/5-down prior, challengers need at least 25 ratings and a 0.03 advantage, and cost only breaks an exact score tie. Technical failures affect availability and fallback telemetry, not quality.

The `query_reason` candidate set keeps OpenAI `gpt-5.6-terra` plus Fireworks `accounts/fireworks/models/muse-glimmer-30b` and `accounts/fireworks/models/inkling` as rating-based challengers that share the family's single 5% exploration budget. Muse Glimmer and Inkling are also available as explicit Fireworks text-route selections in the centralized Spot catalog. Extraction challenger policy remains separate and unchanged.

- `chat` → Fireworks `accounts/fireworks/models/deepseek-v4-flash-0731` for low-latency interactive tool use
- `chat_vision` → OpenAI `gpt-5.6-terra` for image-bearing web and iMessage turns that still need the full chat tool set; ordinary text-only turns remain on `chat`
- `voice_transcription` → OpenAI `gpt-4o-transcribe` for bounded iMessage voice-memo speech-to-text; the resulting transcript continues through `chat` so voice requests retain the normal tools and side effects
- `classification`, `triage`, `extraction`, `extraction_preview`, `requirement_extraction`, `org_memory_extraction`, `email_extraction`, `document_extraction` → Fireworks `accounts/fireworks/models/deepseek-v4-flash-0731` for cheap structured work and high-volume extraction/classification calls

Broker members have no model-routing or provider-key controls.

- Provider deployment shape and capacity belong to cl-router; Spot must not encode provider-hosting or credential guidance in consumer execution paths.

These helpers resolve the permitted route/pin, preserve organization, session, trace, callback, and execution-budget metadata, and make one authenticated router call. Use `generateTextForPublicTask` or `generateObjectForPublicTask` only for public demo or other non-tenant workflows. Feature actions do not construct provider clients, retry provider routes, or bypass these router-only helpers.

Broker organizations do not override routing.

Fallback behavior is router-owned. Spot resolves the operator/global or static route, submits it to cl-router with the remaining execution budget, and never retries through a direct provider. Tool loops preserve the selected route pin and do not replay completed business tools after visible output.

- Provider availability is reported by the authenticated router capabilities endpoint. Missing router credentials or candidate exhaustion produces a typed, sanitized router failure; Spot never interprets local provider-key presence and never changes transport.

Router failures retain the router-owned request ID and sanitized per-attempt provider/model/error category in `modelRoutingEvents` so `/operator/routing` can correlate the persisted router call instead of displaying the configured seed route as an actual attempt.
- Web chat generation in [processThreadChat.ts](convex/actions/processThreadChat.ts) and current-turn iMessage image handling in [handleInboundImessage.ts](convex/actions/handleInboundImessage.ts) use `chat` for text-only turns and `chat_vision` when their emitted model input contains an image part. The shared channel runtime buffers the model run and publishes one completed reply. If a completed tool loop ends blank or truncated, Spot may make one tool-free continuation from the existing tool results on the same router route pin; this is output completion, not provider fallback, and it cannot rerun the business tools.

## Compliance Requirements

Spot now stores contractor/vendor and internal insurance requirements as typed rules. `insuranceRequirements.kind` is `coverage`, `insurer`, or `condition`; `scope` is `own_org` or `vendors`. Coverage rules are keyed by ACORD line-of-business code and store structured `limits[]`, optional deductible ceilings, provisions, and required forms. Insurer rules store carrier standards such as AM Best rating, financial size, and admitted-status requirements. Condition rules store administrative obligations such as cancellation notice, certificate delivery, claims reporting, or subcontractor insurance. Do not reintroduce `category`, `appliesTo`, `evaluationTarget`, or regex requirement semantics.

Uploaded or pasted sources are recorded in `requirementSourceDocuments`, and created requirements keep `sourceDocumentId`, `sourceDocumentName`, `sourceType`, `sourceExcerpt`, and optional source page fields. An own-org requirement source also owns its canonical `certificateHolderId` plus optional deal name/type and internal notes; holder contact and address live on `certificateHolders`. New source imports collect that fulfillment context up front, and connected-mailbox imports seed the sender as holder when safe. Existing sources remain readable without a holder until an admin completes them. `/compliance` groups first by source type/document context so lease, client-contract, vendor-packet, manual, and other requirement sets remain distinguishable, then groups coverage rules by ACORD LOB with separate insurer-standard and condition sections.

Current check state lives in `complianceChecks`, keyed by requirement and subject org. `convex/lib/complianceCheck.ts` performs deterministic coverage checks against structured policy evidence: LOB equality, limit-kind comparisons, deductible ceilings, provision/form detection, expiration, and insured-name matching. Insurer and condition rules are manual in v1 and return `unverified` until an admin verifies them with optional note/evidence/valid-until. The daily vendor compliance monitor records snapshots in `complianceChecks`; `unverified` counts as attention in UI but does not generate vendor gap notifications or follow-up emails. Gap notifications are for `not_met`, `expired`, and `expiring_soon` only.

Surfaces:

- Web: `/compliance` is focused on requirement creation/management. Its top-bar action opens a right-side aside for bulk import or kind-aware manual entry. Vendor orgs also see active client-owned vendor requirements as read-only rows under **My requirements**, labeled as client requirements from the source client org; those rows cannot be archived by the vendor. **My requirements** rows include live compliance status badges (`Met`, `Expiring`, `Not met`, `Expired`, `Unverified`) based on the org's current policies and manual checks. Orgs that are purely vendors hide the **Vendor requirements** tab, while mixed orgs still show both **Vendor requirements** and **My requirements**.
- Connect: `/connect/vendors` is for vendors the org contracts with and monitors against its own standards; active vendor rows hide the invite/note copy, show one of `invited`, `waiting on policies`, `active / noncompliant`, or `active / compliant`, expand into a full requirement checklist with matched policy, limit, expiration, and insured-name details, and link to read-only vendor policy pages under `/connect/vendors/:vendorOrgId/policies`. `/connect/clients` is for clients the org reports insurance requirements to and approves access for. Vendor/client monitoring belongs on these Connect surfaces, not on `/compliance`. Legacy `/connected-orgs/*` paths redirect to the shorter `/connect/*` routes.
- MCP/CLI/REST: compliance requirements and vendor compliance are exposed through `list_insurance_requirements`, `create_insurance_requirement`, `list_vendor_compliance`, `GET/POST /api/v1/compliance/requirements`, and `GET /api/v1/compliance/vendors`.
- Agent: web chat and MCP chat include a vendor compliance snapshot in context so users can ask questions such as “are all my vendors compliant?”
- Broker organizations are supplier records in the operator-managed network. Broker members can maintain their own profile and team only; they do not receive client portfolios, procurement requests, proposals, policies, or cross-organization agent scope. Operators select a broker organization when marketing a client procurement request and keep proposals/private market activity operator-only.
- Agent tools: web chat, inbound email, iMessage, and MCP chat expose `lookup_connected_vendors`, `lookup_vendor_policies`, and `lookup_vendor_compliance` so agents can answer vendor-specific compliance questions with the actual vendor roster, vendor policies, and requirement-by-requirement diffs instead of relying only on the generic requirements summary. MCP write-capable API-key callers may use shared write tools through `ask_spot`; read-only MCP identities receive a tool-level refusal for write operations.
- Agent task control: web chat and iMessage run a deterministic task-control gate before the main agent response path. The gate ranks natural-language cancel/reset candidates with search-style scoring and uses a structured classification model only for plausible ambiguous cases; high-confidence exits clear the active task before workflow-specific guards such as COI completion repair can rewrite the response. Email-specific cancellation remains higher priority than generic task reset.

## Policy Update Broker Emails And Endorsements

Policy updates are explicit external follow-up email work, not an in-Spot case-management workflow. The user-facing flow should feel like: "draft/email this broker contact to update the policy with XYZ." Spot no longer exposes policy-change agent tools, policy-change sidebars, hidden case tracking, broker-reply correlation, or auto-reissue of held certificates after endorsements arrive. General policy-update requests should be handled through the generic email drafting/sending path with the relevant policy context and a recipient explicitly supplied or selected by the operator.

COI endorsement requests use the three-situation model: plain evidence-only certificates issue immediately; endorsement requests already satisfied by policy evidence issue with source-backed citation remarks on the certificate; requests needing new endorsements hold and store a broker email draft on the certificate hold. The user re-requests the certificate after the endorsement arrives.

Endorsement documents still enter the normal policy document extraction/attachment path. `policyUpdateRuns` and `policyDeclarationFacts` remain as source-backed policy update audit/fact storage for appended endorsement documents, but there is no policy-change case lifecycle around them. Full replacement extraction still uses the existing policy extraction pipeline.

## Company Wiki

`orgWikiSections` is the single curated per-org company-context store, replacing the old `orgMemory` row store and, before it, `orgIntelligence`, `businessContext`, dream consolidation, and proactive analysis. The wiki is one markdown document per organization, held as ordered sections so concurrent writers merge instead of clobbering a single blob. It holds stable facts about the company itself: legal structure, headquarters, operations, products, employees, revenue, ownership, compliance posture, and business activities. Do not store policy numbers, policy terms, endorsements, COI/certificate details, email drafts, recipients, attachments, agent/tool limitations, workflow status, user requests, or one-off tasks. Policy and endorsement facts must come from source-backed policy tools and first-class policy tables, not the wiki.

### Schema: `orgWikiSections`

`convex/lib/orgWiki.ts` owns the fixed section catalog (`profile`, `operations`, `scale`, `compliance`, `preferences`, `notes`), the assembly into one markdown document, and the bullet rendering. Each row has:

- `orgId`
- `key` / `heading` / `order` — the canonical section, its rendered heading, and reading order
- `body` — the whole section as markdown, normally a bullet list
- `source` — `extraction` | `analysis` | `chat` | `email` | `imessage` | `slack` | `manual` | `operator` | `mcp`
- `sourceRefs` — stable evidence references used for idempotent automated writes
- `proposedBody` / `proposedRationale` — a pending machine update on a manually edited section
- `manuallyEditedAt` — set once a human writes the section, which converts later machine updates into proposals
- `createdAt` / `updatedAt`

No embeddings, no ranking, no relevance cutoff. Agents read the whole assembled document: the section catalog bounds its size, so the prompt gets every fact rather than a ranked subset that can drop the one line that mattered. Every automated line — conversational `saveNote`, mailbox/document extraction, and the operator agent's confirmed section write — passes the company-context gate in `convex/lib/orgWikiPolicy.ts`; schema-validated extraction paths pass `trusted` to allow phrasing the free-text agent tools must not use. Human section writes from Settings, the operator console, and tenant MCP are admin-gated but not content-gated. Bullets are deduplicated and sorted, so a rerun over unchanged sources produces a byte-identical body. `extractedLines` records which bullets the company-information reconciler owns: it rewrites and retracts only those, so a reconcile that has nothing to say about a section leaves the conversational and append-only writers' lines in place rather than emptying it. A manually edited section is human-owned end to end and receives a reviewable replacement proposal, never a silent merge, and no proposal at all when the sources yield no facts for it. Automated mailbox and document extraction uses structured output with a section-routing field and a high-confidence threshold. Settings → Agent → Company wiki is the client frontend: all current direct members may read it, while only current direct admins may rewrite a section or resolve a proposal. Operators manage the same store at `/operator/clients/:clientOrgId/wiki`; both the UI and backend writes become read-only during impersonation. Tenant MCP exposes exact-token-organization read and section writes through `read_company_wiki` and `write_company_wiki_section`, with current membership on reads and current direct-admin plus OAuth write scope on writes. These replace the removed `list/create/update/delete_company_memory` tools; external MCP clients pinned to those names must migrate. Operator MCP receives the exact-confirmed client-wiki tools from the operator registry.

## Request Packet Composition

Durable client knowledge lives in one place, the company wiki (`orgWikiSections`); there is no org-scoped procurement store. `listPacketSections` in [convex/procurementPacket.ts](convex/procurementPacket.ts) composes the client's wiki with the request's own sections on read, so a new request starts with the client's background and later wiki edits reach requests already open. Composition is operator-audience only: the client projection in `clientProcurementRequests.ts` and the broker `/share/packet` projection assemble the request packet alone and never receive wiki content. Extraction routes a stable placement preference to the wiki `preferences` section and a market's documentation demand to `compliance`; broker appetite belongs on `brokerProfiles`, not on a client.

## Connected Email (IMAP)

Users can connect generic IMAP mailboxes from Settings → Email. The default access scope is user-only; users can opt into org scope so direct client-org members and agents acting for that org can search the mailbox. Access scope is separate from the three per-mailbox automation controls: policy imports, requirement imports/compliance checks, and durable company-context extraction. Broker organizations have profile/team access only and do not receive client mailbox access. Spot stores account metadata, encrypted credentials, automation settings, scan cursors, and bounded outcome/audit metadata; it does not persist raw mailbox bodies during ordinary search/read or proactive classification. IMAP passwords/app passwords are encrypted server-side with `EMAIL_CONNECTIONS_ENCRYPTION_KEY` and are never returned to the browser or agent tools. New connections enable all three automation controls after an explicit disclosure that imported policies, requirements, and company wiki facts become workspace data visible to organization members; mailbox activity threads remain private to the mailbox owner. Legacy personal mailboxes remain on-demand until configured; legacy organization mailboxes retain alert-only behavior until configured.

Agent mailbox tools perform live IMAP search/read, read bounded text from selected PDF/DOCX/text-like attachments, save mailbox attachments or the email message itself into the current thread for reuse, import selected PDF attachments into the existing bound-policy extraction pipeline, import email bodies and lease/contract/vendor requirement attachments into internal or vendor compliance requirements, and send connected-vendor invites when the user requested that action. Complex mailbox tasks should go through the `mailbox_coordinator` model route (Fireworks GLM 5.2 by default), which can call live mailbox tools and existing Spot import actions. Main web chat exposes the mailbox coordinator as a single tool and stores a `mailbox_task` artifact so the message shows a compact background-process opener and the right panel shows the coordinator's plan, search audit, specific email evidence, and user-confirmed buttons to save attachments to the thread, import policy documents, plus create vendor/internal requirements; the direct mailbox search/read/import tools remain behind the coordinator rather than being attached to every chat request. Coordinator searches are intentionally agentic: it derives targeted search terms and explicit `dateFrom` / `dateTo` windows from the user's request, searches all accessible connected mailboxes unless the user selected `/` mailbox targets, ignores messages sent from `spot.insure`, `spot.claritylabs.inc`, or their subdomains to prevent reference loops, inspects promising messages, then broadens or pivots terms/date ranges before concluding that an item is missing. When the coordinator identifies attachments the user may need again, it should save them to the thread with `save_connected_email_attachments_to_thread`; saved thread attachments are stored in Convex file storage on a `threadMessages` row and are available to the email expert as uploaded-file attachments without another mailbox search. When the user asks to attach, forward, preserve, or provide proof of an email whose useful content is in the email body, the coordinator should use `save_connected_email_message_to_thread`, which exports the message as an attachable `.eml` file before drafting or sending. For web chat, the coordinator writes a running `mailbox_task` artifact onto the current agent message as soon as it has a plan, so the thread shows an auditable background process while the live IMAP search is still running. For iMessage/text requests, the coordinator generates a short plan first and sends a status text before running the live mailbox workflow. Imported policies, requirements, vendor invites, notes, and thread artifacts are persisted through their existing first-class tables; raw mailbox messages remain remote unless a user-directed import stores an attachment/artifact.

Web chat also exposes `render_email_preview` for outbound email drafts. It renders the current or specified `pendingEmails` draft through Playwright as a PNG screenshot or PDF printout, stores the rendered file in Convex storage, and attaches it to the current assistant message so users can inspect email formatting without sending. Runtime environments need Playwright's Chromium browser installed; if the browser binary is missing, the tool returns a renderer-unavailable result instead of fabricating a preview.

Outbound emails are persisted as `pendingEmails` and email `threadMessages`. Sending assigns a deterministic RFC `Message-ID` and uses the thread-specific email address as Reply-To when available, so replies can be correlated back to the original thread. General policy-update requests should be handled as Spot email drafts through the generic email tooling; Spot no longer opens hidden policy-change cases or uses endorsement-specific completion tools.

Daily connected-mailbox automation runs from the Railway cron service in `mailbox-scan-worker/`. The worker starts once daily at `0 15 * * *` UTC, calls `POST /cron/connected-email/scan` on the Convex site URL, and exits. The HTTP route validates `EMAIL_SCAN_CRON_SECRET` as a Bearer token and then calls the internal action `actions/connectedEmailScan.scanAllMailboxes`, which scans active legacy org mailboxes plus any personal or org mailbox with at least one automation control enabled; `actions/connectedEmailScan.scanOrgMailboxes` runs the same bounded flow for one org. The proactive scan engine lives in `convex/actions/connectedEmailScan.ts`; interactive mailbox tools and import pipelines stay in `convex/actions/connectedEmail.ts`, and shared IMAP connection/crypto/parse helpers live in `convex/lib/imapMailbox.ts` (node-only). The first scan searches the last 400 days for insurance-relevant subject terms, processes the newest 50 matches oldest-first, then advances to the live high-water mark so historical mail cannot starve new arrivals. Later runs process up to 50 new messages in UID order. A message the IMAP fetch cannot read is retried on later scans and, after three failed attempts, its automation item is marked `skipped` with the fetch error so the UID watermark advances past it instead of stalling the mailbox forever; the incomplete-scan attention notice fires only on the first failure. Discovery reads IMAP envelope/body-structure plus at most 64 KB from one text part, rejects Spot-originated loops, classifies bounded batches through the `mailbox_coordinator` route with short stable candidate IDs, and records UIDVALIDITY-aware cursor/outcome metadata for retry safety. Policies reuse the bound-policy extraction pipeline with SHA-256 duplicate guards, requirements reuse the compliance importer and final-policy assessment, and company facts reuse the company-wiki evidence/dedupe policy. Missing, unreadable, or ambiguous items create replyable proactive threads and route external delivery through the user's Profile → Proactive conversations preference (`email`, `imessage`, or both) via the shared notification system. Thread-linked review items render as one subject pill per email in the agent message. A pill fetches the live email without persisting its body and opens a dedicated review sidebar; the footer can mark the message not relevant or import its policy/requirements, then removes the resolved pill. Raw messages remain remote unless an existing import path deliberately stores an attachment or thread artifact.

Users who can manage a mailbox (the owner, or an org admin for org-scoped mailboxes) can also run a manual scan over an explicit date range from Settings → Email → mailbox drawer. The public action `actions/connectedEmailScan.scanMailboxRange` searches the range without subject-term filtering, scans the newest 50 matches with the same classification/import pipeline and automation-item ledger (already-processed messages are skipped), and reports scanned/processed/attention counts plus truncation. Manual scans never move the incremental UID watermark and never record unreadable-message attempts, so they cannot affect the daily scan's cursor or poison-pill retry budget.

## cl-sdk Integration

The Spot-specific `cl-sdk` wiring lives under `convex/lib/`.

- [sdkCallbacks.ts](convex/lib/sdkCallbacks.ts): adapts every `cl-sdk` model and embedding callback to the router-only, fail-closed execution path
- [extraction.ts](convex/lib/extraction.ts): builds a preconfigured extractor
- [documentMapping.ts](convex/lib/documentMapping.ts): maps SDK documents to Convex policy records
- [extractionFieldReview.ts](convex/lib/extractionFieldReview.ts): reusable evidence-backed field review groups for missed or contradicted extracted fields
- [extractionPostProcess.ts](convex/lib/extractionPostProcess.ts): shared post-extraction quality pipeline before policy persistence
- [agentPrompts.ts](convex/lib/agentPrompts.ts): SDK prompt exports plus Spot retrieval-backed context builders

### Callback Contract

Current `cl-sdk` passes document content through callback `providerOptions`.

- `providerOptions.pdfBase64` is legacy/non-extraction helper input only. Policy extraction must pass preprocessed `sourceSpans`; do not add new raw-PDF extraction or page-map flows.
- `providerOptions.parsedPdfText` carries full parsed text for helper flows that pre-extract attachment text before calling a model.
- `providerOptions.images` carries page images when PDF-to-image conversion is used.
- `providerOptions.sourceSpans` carries parser-derived source evidence. The v3 path builds a source-node hierarchy and operational profile from those spans; model calls may label/group existing nodes or cite facts, but canonical wording and PDF provenance remain in `sourceNodes`/`sourceSpans`.
- `trace` metadata identifies task-specific extraction/model batches for operator model-call debugging. Preserve it in extraction trace events.

Spot translates those into AI SDK multipart message content in `sdkCallbacks.ts`:

- PDFs become `{ type: "file", data, mediaType: "application/pdf" }`
- images become `{ type: "image", image, mediaType }`
- Parsed PDF text is already injected into those helper prompts and preserved in `providerOptions.parsedPdfText`; Spot callbacks do not convert it back to a PDF file part.

Notes:

- The `providerOptions.images` items from `cl-sdk` do not carry a `type` field; Spot adds `type: "image"` when building AI SDK parts.

### Extraction Shape

Spot treats the v3 source tree as canonical extraction truth. `PolicyDocument`, `documentMetadata`, and `documentOutline` are compatibility projections for existing surfaces. Keep SDK interpretation labels (`type`, `label`, `interpretationLabels`) as hints inside the original source hierarchy. Do not regroup source text into Spot-owned buckets when a source tree is available.

Spot persists:

- Top-level policy financials: `premium`, `totalCost`, `taxesAndFees`, `premiumBreakdown`, `minPremium`, `depositPremium`
- Extracted dates are normalized to `MM/DD/YYYY` before persistence where the source value is parseable. Monetary and limit-like fields keep user-facing display strings while also storing numeric companions such as `premiumAmount`, `totalCostAmount`, coverage `limitAmount` / `deductibleAmount`, and row-level `amountValue` for deterministic comparison.
- Source document structure: `sourceNodes` rows plus top-level `documentMetadata` and `documentOutline` projections. Existing rows may lack source nodes; source-native preview surfaces should show a rebuild/re-extraction warning instead of pretending legacy categories are equivalent to the original document structure.
- Operational policy profile: `operationalProfile` stores source-backed metadata, parties, ACORD lines of business, coverage lines, limits, deductibles, premiums, key dates, and endorsement support with `sourceNodeIds` and `sourceSpanIds`. Keep policy classification in `linesOfBusiness`; do not add a parallel `policyTypes`, `coverageTypes`, `coverageOrigin` bucket, or deterministic coverage-origin projection.
- Legacy document detail may still exist under `document.sections`, `document.definitions`, `document.coveredReasons`, `document.endorsements`, `document.exclusions`, and `document.conditions`, but it is not canonical extraction truth.
- Declarations and supplementary facts as top-level policy fields
- Raw source evidence in `sourceSpans`; retrievable hierarchy in non-vector `sourceNodes`; compatibility source windows in non-vector `sourceChunks`. Source spans preserve `sourceUnit`, `parentSpanId`, table location, page/character location, bounding boxes, and stable `sourceSpanIds`; `sourceSpans.listSpansByPolicyAndSpanIds` returns requested spans plus related parent spans so table-cell facts can highlight their parent row or fall back to the source page. Client-facing source-span lookups are capped for page stability; individual visible rows should query their own narrow evidence IDs instead of asking for every source span in a policy at once.
- Spot runs all post-extraction cleanup through `postProcessExtractionDocument()`: deterministic policy-period fallback, evidence-backed field review, `insuranceDocToPolicy()`, coverage declaration scoping, review-copy polish, and organization-name normalization. Keep new cross-cutting extraction cleanup in this pipeline rather than adding one-off fallback extractors inside `policyExtraction.ts` or `documentMapping.ts`.
- Field review is configured as reusable groups in `extractionFieldReview.ts`. It uses source spans and document sections, applies only evidence-quoted corrections for registered fields, and runs on the low-cost `classification` route. `EXTRACTION_FIELD_REVIEW_MODE=skip|auto|always` controls whether it is disabled, runs only for missing group fields, or runs for all groups with evidence.
- The policy-period fallback still performs a deterministic source-span check over raw PDF text before persistence. Clear `PERIOD OF INSURANCE` / `POLICY PERIOD` / `POLICY TERM` source text, including day-month-year table layouts, is allowed to override missing, malformed, or conflicting SDK `effectiveDate` / `expirationDate` values.

### Token Limits

Spot avoids low artificial max-output caps for SDK-facing extraction calls.

- `cl-sdk` resolves task preferences for diagnostics, but when model capabilities expose `maxOutputTokens`, the SDK uses that upper bound as the request cap.
- `sdkCallbacks.ts` re-resolves the effective cap from the actual Spot route selected for the call. Broker or operator model overrides therefore use the selected route's known max output limit instead of the static SDK hint.
- Do not add prompt-specific low max-token overrides for extraction unless the provider itself has a lower hard limit.

## Policy Extraction

Two entrypoints, both PDF-only:

- [convex/actions/extractFromUpload.ts](convex/actions/extractFromUpload.ts) — `extractFromUpload` (public action) for direct user uploads; `extractFromUploadInternal` (internal action) for the email agent.
- [convex/actions/extractPolicy.ts](convex/actions/extractPolicy.ts) — internal helpers used by the email agent via the `extract_policy_attachment` tool.
- [convex/actions/reExtractFromFile.ts](convex/actions/reExtractFromFile.ts) / [retryExtraction.ts](convex/actions/retryExtraction.ts) — re-run and retry.

### Flow

1. Fetch or receive a PDF.
2. Store the raw PDF in Convex file storage.
3. Load the PDF bytes from Convex file storage. If the LiteParse worker endpoint is configured, attempt conversion once, then use its parsed text plus hierarchical source spans and run `buildExtractor().extract(pdfBytes, documentId, { sourceSpans })`. If conversion is unavailable, fall back directly to local PDF.js source spans and call the same source-span extraction path. Do not pass a signed storage URL into `cl-sdk`; review and follow-up extractors can run long enough that repeated URL fetches become unreliable.
4. Verify critical policy-period dates from source text when a clear declaration-page period is present, then map `InsuranceDocument` into Spot policy fields.
5. Run coverage declaration scoping before persistence. When the SDK extracts multiple limits for the same coverage and limit role, Spot scores declarations, selected-option markers, summary/confirmation pages, endorsements, and source-span evidence; persists only the best current coverage value; and stores `extractionReview.questions` for any same-role limit conflict that still needs client/broker confirmation. Distinct limit roles such as per-occurrence and aggregate remain separate coverage rows.
6. Persist the extracted document and metadata.
7. Chunk the structured document when compatibility/runtime paths still need `documentChunks`, and embed only those chunks with `text-embedding-3-small`.
8. Store `sourceNodes` as the canonical non-vector hierarchy, store `sourceSpans` for exact PDF highlights, and keep non-vector `sourceChunks` plus embedded `documentChunks` only as compatibility artifacts for old paths.

Pipeline runtime state:

- Policy extraction status remains denormalized on `policies.pipelineStatus` / `pipelineError` for fast list filtering.
- High-churn extraction runtime state lives in `policyExtractionRuns`: `pipelineCheckpoint`, `pipelineLog`, leases, heartbeat timestamps, and detailed progress. This avoids rewriting large policy documents for every log, checkpoint, and heartbeat. Large `cl-sdk` checkpoint payloads and extraction-to-embedding payloads are stored in Convex file storage and tracked by `policyExtractionArtifacts` records keyed by policy/job ID and artifact kind. The pipeline checkpoint only keeps compact storage IDs and summaries. `cl-sdk` assemble checkpoints intentionally omit the assembled document before storage, because the document can be rebuilt from checkpointed extraction memory and storing both memory and document can make the checkpoint artifact too large.
- Durable operator debugging history lives separately in `policyExtractionTraceSessions` and `policyExtractionTraceEvents`. Each upload/full retry starts a new trace session; resume retries reuse the checkpoint's `traceId` when available. Trace events record phase timing, pipeline logs, model-call metadata, external-worker events, embedding batch summaries, token usage, provider/model/route-source/transport, durations, errors, and bounded model-call debug previews. The debug payload redacts raw PDF/base64 payloads, stores attachment summaries instead of file bytes, truncates prompt/output text, and the daily `extractionTraces.sweepExpired` cron removes records after 90 days.
- Query surfaces such as `policies.get` and `policies.getInternal` merge runtime state from `policyExtractionRuns`, falling back to legacy fields on `policies` for old in-flight jobs.
- The extract phase stores `documentChunksForEmbedding`, `sourceSpansForStorage`, `sourceNodesForStorage`, and compatibility `sourceChunksForEmbedding` in a storage-backed `embedding_payload` artifact before advancing to `embed_and_store`, so a resumed storage phase can reload transient artifacts without inflating checkpoint documents. Only `documentChunksForEmbedding` are embedded; source spans, source nodes, and source chunks are stored as non-vector evidence records. Artifact blobs are cleaned up after durable embedding/source-span/source-node storage succeeds, cancellation, terminal success, and full restart; generic errors keep artifacts for resume/retry.
- External extraction completion payloads are stored as `external_completion_payload` artifacts before Convex finalization. If a policy is stuck after this artifact is saved, retry the same extraction run rather than starting a fresh upload/restart; the external worker first calls `completeExternalExtractFromStoredPayload`, verifies the active lease/checkpoint still matches, and replays the stored payload into the normal finalization path. Do not replay across a newer extraction run or after cancellation.
- Extraction now uses the source-span SDK path only. LiteParse/PDF.js preprocessing must produce `sourceSpans` before calling `cl-sdk`; the old raw-PDF page-map, focused-extractor, formatter, form-inventory, broad-review, and SDK checkpoint/resume paths have been removed. The SDK builds operator source nodes for evidence/search but feeds operational-profile extraction from compact source-span evidence windows so model time is spent on end-user facts rather than display-tree repair. The extraction worker's outer full-job loop uses `EXTRACTION_JOB_CONCURRENCY` (default 8, bounded 1-1000), while provisional jobs use `EXTRACTION_PREVIEW_CONCURRENCY` (default 2, bounded 1-8). PDF-bearing work is separately admitted before full/preview job claim or HTTP body decoding: `EXTRACTION_PDF_WORK_MAX_ACTIVE` defaults to 12 total live PDFs and `EXTRACTION_PDF_WORK_MAX_FULL_ACTIVE` defaults to 8 full extraction PDFs, reserving capacity for preview and HTTP traffic even when production's outer job ceiling is 1000. Waiters retain only job/request metadata, not file bytes. Those limits do not parallelize the native parser: `convertPdfWithLiteParse` serializes every full, preview, and HTTP conversion within a worker process, caps its defensive wait queue at `LITEPARSE_MAX_QUEUED_DOCUMENTS` (default 12), prioritizes latency-sensitive preview and HTTP conversions in bounded four-start bursts so every waiting class progresses, and drops aborted HTTP conversions from the queue. Authenticated HTTP conversion installs upload, response, and socket cancellation listeners before admission and body parsing so a caller timeout cannot leave its decoded PDF queued. Convex makes one synchronous conversion attempt per preprocessing path and falls back directly to PDF.js on failure or timeout. Embedding defaults to 8 concurrent embedding calls (`EXTRACTION_EMBEDDING_CONCURRENCY`, bounded 1-16).
- Long-running SDK extraction can be offloaded to the standalone Railway worker in `extraction-worker/` by setting `EXTRACTION_WORKER_MODE=external` and a shared `EXTRACTION_WORKER_SECRET` on Convex, then running the worker with `CONVEX_URL` and the same secret. In external mode Convex remains the durable job ledger: uploads/full retries run the bound-policy document gate in Convex before handoff, then create `policyExtractionRuns` checkpoints, the worker claims extract-phase leases, heartbeats, completes extraction, and hands the job back to Convex for embedding/source-span persistence and post-processing. Explicitly labeled specimen policies bypass model classification and are accepted as extraction-testing fixtures even when they disclaim bound coverage or evidence of insurance. A rejected new upload row is marked `not_insurance`, auto-archived, and never enqueued; rejection during re-extraction, renewal, or a full retry keeps the existing bound policy and canonical extraction run operationally complete, retains the compact replacement checkpoint for retry, and records the rejected attempt as an errored trace session. Replacement runs persist an explicit promotion boundary before writing replacement fields or files: failures before that boundary leave the prior final policy operationally complete, while failures at or after promotion fail the policy closed so final-only workflows cannot consume replacement fields without fully persisted source evidence and post-processing. Re-claiming an extract-phase job restores a missing preview queue row when the provisional extraction never delivered, so worker crashes cannot permanently drop the fast preview. Workers send their protocol, worker version, and `@claritylabs/cl-sdk` dependency on each claim; Convex rejects incompatible workers before leasing jobs, and deployed dev/production environments should set `EXTRACTION_WORKER_EXPECTED_CL_SDK_VERSION` to the current extraction-worker package spec so stale workers cannot silently leave uploads at “Extraction starts shortly.” After any SDK or router-policy bump, verify both shared package specs with `npm run check:shared-package-versions`; for SDK changes, compare Convex `/agent-health` `extractionWorker.expectedClSdkVersion` against the extraction worker `/health` `clSdkVersion`, then run the production deployment health audit before starting production extractions. The claim action returns resolved model routes without provider credentials so trusted workers preserve extraction/classification overrides. The same worker also exposes authenticated `POST /liteparse/convert` when `PORT` is set; configure Convex with `EXTRACTION_WORKER_URL` plus `EXTRACTION_WORKER_SECRET` so requirements imports, mailbox attachment reads, on-demand source lookup, supplementary extraction, and chat/email/iMessage PDF attachment context can use LiteParse text with PDF/PDF.js fallback.

Cancellation:

- `policies.cancelExtraction` marks `pipelineError` as `Cancelled by user`.
- `policyExtraction.ts` checks that flag before phases and before/after each `cl-sdk` model call. Cancellation stops at the next provider-call boundary and is recorded as an expected pipeline error, not as a transient action failure.
- `policyExtraction:advance` uses a Convex-backed checkpoint lease before running a phase. This prevents overlapping scheduled advances from running the same long extraction phase concurrently and racing to overwrite extracted policy data. The lease is heartbeat-based and watchdog-scheduled, so if an advance action dies during a long provider call, a later advance can reclaim the checkpoint after the heartbeat goes stale instead of leaving the policy stuck in `running`. A five-minute cron (`policyExtraction.sweepStale`) also scans `policyExtractionRuns` by `pipelineStatus`/`updatedAt` and requeues stale running checkpoints, or marks runs with no resumable checkpoint as errored.

## Retrieval And Agent Context

Spot uses vector-backed document/conversation stores plus list-based source evidence:

- `sourceNodes` — canonical source-tree hierarchy, ranked lexically and expanded by hierarchy for policy wording
- `sourceSpans` — exact PDF evidence/highlight layer
- `sourceChunks` — non-vector compatibility source-span windows for policies not yet rebuilt into source nodes
- `documentChunks` — legacy extracted policy structured fact chunks, secondary only
- `conversationTurns` — legacy raw cross-thread conversation memory table, no longer written or injected into prompts; clear it with the operator memory purge when cleaning an environment
- `orgWikiSections` — the curated company wiki, read whole and gated by the wiki policy

[agentPrompts.ts](convex/lib/agentPrompts.ts) owns the source-backed retrieval builders used by on-demand tools and non-interactive workflows. Authenticated conversational surfaces do not call these builders eagerly before every model turn:

- `buildDocumentContext()` — embeds the query only for secondary `documentChunks`, ranks source nodes lexically, expands hierarchy context, and attaches stable `sourceSpanIds`. If only legacy chunks exist, it queues `ensurePolicyV3SourceTree()` and warns that exact policy-wording answers require source-tree rebuild.
- `lookup_policy` loads fresh structured summaries only when called and accepts search text, up to five exact policy IDs, or `expiringWithinDays`. `lookup_policy_section` owns detailed source retrieval and queues a missing source-tree rebuild on demand.
- `lookup_policy_section` uses [policyLookup.ts](convex/lib/policyLookup.ts) in web chat, inbound email, iMessage, and MCP chat to return source-node matches with hierarchy path, excerpts, `sourceNodeIds`, `sourceSpanIds`, and PDF location metadata. It still falls back to raw source spans or on-demand PDF parsing for older policies, but source-node evidence is preferred.
- `confirm_policy_fact` lets agents confirm a concise policy fact after `lookup_policy_section` returns supporting original-PDF `sourceSpanIds`. The tool may patch only a constrained set of top-level policy fields when the cited PDF text directly supports the update, and records policy audit history rather than long-term memory.
- `buildConversationMemoryContext()` — intentionally returns no context; raw conversation memory should not steer future answers.
- Web chat composer steering lives in [components/spot-prompt-input.tsx](components/spot-prompt-input.tsx) and [convex/agentTargets.ts](convex/agentTargets.ts). Typing `@` opens a custom picker for policies and requirements; typing `/` opens accessible connected mailboxes. Selected targets are stored on the user `threadMessages` row as `referencedPolicyIds`, `referencedRequirementIds`, and `referencedMailboxIds`. Policy selections are injected as validated ID-only focus and require a fresh policy-tool call; explicitly selected requirements and mailboxes retain their workflow-local context. Without a current policy selection, [agentPolicyFocus.ts](convex/lib/agentPolicyFocus.ts) may carry only the immediately previous completed response's referenced policy IDs, capped at five and revalidated for scope/archive state; carried IDs are not persisted again unless a tool actually uses them. Selected mailbox IDs are passed into [mailboxCoordinator.ts](convex/actions/mailboxCoordinator.ts), which restricts live IMAP search to those accounts unless the user asks to broaden the search. When a user submits while an agent response is active, the web composer queues that message locally and sends it after activity ends; the queued row's **Send now** action sends immediately, cancels the in-flight agent message, and lets the new message steer the thread.
- Agent thread UI lives under [components/agent-thread](components/agent-thread). [app/agent/thread/[id]/page.tsx](app/agent/thread/[id]/page.tsx) should stay route/AppShell orchestration only; reusable message rendering belongs in `thread-content.tsx`, shared thread shapes in `types.ts`, and artifact-specific summary cards, right panels, and normalization helpers under `components/agent-thread/artifacts/`. User messages own the avatar, sender, channel, and timestamp identity row; agent messages, thinking states, and confirmations render without an agent identity row.

## Convex Patterns

Auth pattern:

- Public Convex functions have user auth context.
- Internal functions do not.
- Never call a public function that depends on `requireAuth()` from an internal action.

Storage and retrieval pattern:

- `policies.document` stores the structured extracted document.
- `sourceNodes` stores canonical non-vector policy hierarchy; `documentChunks` is the remaining embedded policy compatibility corpus.
- The company wiki stores curated company-context facts only. Policy, endorsement, COI, thread, email, and workflow facts live in their first-class tables and must be retrieved with tools.

Important: in a Conductor worktree, `npx convex dev` and `npx convex dev --once` update only that worktree's native local deployment. They do not update shared dev or production. Production Convex deploys through `.github/workflows/deploy-convex.yml` on every `main` push so the release-ready check exists for every Vercel candidate; use manual `npx convex deploy --yes` only for an explicitly approved recovery. ## Main Product Flows

### Onboarding

Onboarding is role-specific.

- `/signup` opens the client email/OTP form directly; `/signup/client` remains a compatible entrypoint. Broker accounts are provisioned by operators.
- `/onboarding` routes broker organizations to `/onboarding/broker`; new users without an organization and client users continue to `/onboarding/setup`.
- Client setup has three steps: identity (name, role, optional phone), organization (name and optional website enrichment), and finish. Policy uploads are operator-only and are not offered during client onboarding. Finish shows an agent email only when the organization has a configured handle.
- `/broker/team` hosts the shared team settings actions and sidebar through `SettingsActionsContext`, including member editing and invitations.

Passport onboarding (`/onboarding/passport/*`) has been removed.

### Email Agent (Inbound)

Inbound email arrives at `POST /resend-inbound` and is handled by `convex/actions/handleInboundEmail.ts`.

- No hardcoded intent routing. The agent runs chat through the shared `chat` model route and a tool set:
  - `lookup_policy`
  - `lookup_policy_section`
  - `confirm_policy_fact`
  - `compare_coverages`
  - `email_expert` — delegates outbound drafting/sending to the shared email subagent when the sender is an authenticated internal team member in direct mode
  - `save_note` — writes only explicit stable company facts into a company-wiki section
  - `generate_coi`
  - `extract_policy_attachment` — extracts PDF attachments via `extractFromUploadInternal`
- Email replies do not automatically write observations to memory.

### iMessage Agent (Inbound)

Inbound iMessage arrives through the `imessage-worker` Spectrum bridge and `POST /imessage-inbound`. Direct chats and group chats share the same handler in `convex/actions/handleInboundImessage.ts`.

- The worker forwards the Photon chat GUID, group flag, chat title, sender address, and participant roster when available.
- Convex stores group-level state in `imessageChats` and one row per participant in `imessageParticipants`; do not create auth `users` rows for unlinked group participants.
- If no participant in a group has a linked Spot phone number, Spot sends the signup fallback and asks the worker to leave the group.
- If one or more linked participants resolve to the same org, the group runs in single-org mode while preserving anonymous speaker labels for context.
- If linked participants resolve to multiple orgs, the agent may read context from the linked orgs represented in the group, but write actions require an unambiguous org/policy and a linked current sender. Mutating tools should fail closed rather than guessing across orgs.
- Thread routing for iMessage groups uses `threads.imessageChatGuid`; legacy direct-chat routing by `threadPhone` is retained for fallback/proactive sends.
- Agents can create new outbound iMessage group chats only after explicit user confirmation. Group creation resolves the requester plus named teammates, client-specific broker contacts, broker/client/vendor org members, or explicit phone numbers, then calls the `imessage-worker` private `/send` API with a `participants` payload. Production uses Photon Advanced iMessage chat creation; terminal mode simulates a deterministic group GUID for dev. Created groups are synced into `imessageChats` / `imessageParticipants` and routed through `threads.imessageChatGuid`; unlinked phone numbers remain anonymous participants and do not create auth `users` rows.
- Client-specific broker group-chat resolution prefers the primary `brokerClientAssignments` producer for that client, then the broker org's `primaryInsuranceContactId`, then a broker admin/member with a phone number. Broker admins can update the client-specific broker contact from the client list.

### Spot Agent Email Sending

Outbound emails sent by Spot Agent are centralized in `convex/lib/emailSubagent.ts`.

- Channel agents should delegate draft/send/forward requests to the `email_expert` tool instead of hand-rolling email payloads.
- The email subagent owns recipient caution, formatting, signatures, attachment preparation, Resend payload construction, pending-send scheduling, and sent-email thread records.
- It can attach original policy PDFs from `policies.fileId`, user-uploaded files already present in the conversation, and generated COI PDFs from `generateCoi.run`.
- `generateCoi.run` stores every newly generated COI PDF in Convex file storage, records file history in `certificates`, and records holder/version identity in `certificateHolders`, `policyCertificates`, and `certificateVersions`. Treat the lifecycle tables as the source of truth for certificate holder contact, snapshot, version, request kind, request signature, requirement-source identity, and reuse details. Legacy `certificates` rows are file-history rows only; do not bridge them back to lifecycle IDs or backfill old certificate rows. Browser generation uses the shared batch action for either one policy or one requirement source. Programmatic generation is exposed through the legacy policy REST route, the general `POST /api/v1/certificates/generate` route, and MCP/CLI tools (`list_policy_certificates`, `generate_policy_certificate`).
- Certificates are broker-owned informational COIs and must include the ACORD-style disclaimer: `THIS CERTIFICATE IS ISSUED AS A MATTER OF INFORMATION ONLY AND CONFERS NO RIGHTS UPON THE CERTIFICATE HOLDER.` Holder-only requests generate or reuse immediately from holder information; holder address is optional. Additional-insured requests run a source-backed policy evidence gate: supported requests generate a certificate showing the holder and additional insured, while unsupported, ambiguous, or conflicting requests create a broker follow-up draft/request and do not generate a certificate. Other endorsement-bearing requests should route to broker follow-up rather than certificate generation.
- Structured recipient direction is carried by the `email_expert` tool and resolved against configured broker/requester identities; prose regexes never choose a recipient. `convex/lib/coiAttachmentGuards.ts` owns structural attachment authorization. Original policy PDFs require an explicit `original_policy_document` intent with an exact policy and recipient, and every multi-COI send revalidates the persisted recipient, ordered file IDs, draft fingerprint, actor, and confirmation record at the final sender.
- It requires confirmation instead of sending when the recipient email is inferred or unknown, the body/subject is incomplete, attachments are ambiguous, or the current request is draft-only. An affirmative current-turn instruction to send, email, forward, or "draft and send" may deliver the generated single-recipient draft without a second round trip only when the persisted source message is bound to the current actor, organization, and thread; negated, advisory, quoted, older-turn, and uncertain send language remains draft-only. A recipient outside known contacts is eligible on that path only when the source message contains the exact address. There is no organization-wide auto-send setting; unattended vendor-compliance follow-ups always remain drafts for review. Clicking Send or issuing a follow-up typed, iMessage, MCP, or CLI send command confirms the exact persisted draft; neither path bypasses missing recipient/subject/body fields or COI attachment safety guards, and multi-COI batches still require confirmation of the exact recipient and ordered file set. Web-chat approval phrases send deterministically only when the immediately preceding response is linked to that one persisted draft, so an unsupported claim that a different or revised draft is ready cannot send a stale artifact. Agent-approved sends update and transition the existing thread-and-recipient draft to pending/sent rather than creating a second active row; scheduling also cancels any older duplicate drafts for that recipient. Agent prose must not claim a draft was updated or an email was sent unless the email tool result confirms it.
- Web chat, inbound email, iMessage, and MCP/CLI surfaces all route directed outbound email through shared email-draft primitives rather than hand-rolled send paths. The shared email identity falls back to `agent@${AGENT_DOMAIN}` when no custom agent handle is configured. Web chat and iMessage pass the current user's email/name as the default recipient so "email me" requests resolve without asking for already-known contact details. The `bccRequesterOnAgentEmails` org setting defaults on and blind-copies the requesting team member on directed outbound emails. The email expert supports structured `cc` and `bcc` recipients.
- In web chat, draft emails are persisted as native email-channel thread messages backed by a `pendingEmails` draft. The chat still shows a concise assistant note that an email was drafted, while the full copy lives in the email card/right-side preview. The user can review or quickly send from the draft card, send/cancel from the resizable right-side email preview panel, or use typed chat approval as a fallback that sends the current draft artifact instead of requiring a regenerated draft message. Right-side previews can stack, so an email draft and PDF/policy preview may be open at the same time; when stacked, panels begin at equal widths with the main content and the PDF panel stays furthest right.
- MCP and local CLI expose the same durable draft lifecycle through `list_email_drafts`, `draft_email`, `update_email_draft`, `send_email_draft`, and `cancel_email_draft`. Programmatic tools should update the existing draft artifact in place and send/cancel by draft ID; `ask_spot` remains for Q&A and contextual reasoning.
- Pending emails persist attachment metadata in `pendingEmails.attachments`; the scheduled sender writes those attachments back into the unified thread email message after Resend accepts the send.

### Agent Q&A (Chat)

1. Load org context, policies, and the company wiki.
2. Build retrieval-backed document context + curated company-memory context.

## REST API

Versioned REST API under `/api/v1/*`. All routes require:

- `Authorization: Bearer <token>` (OAuth token from `/oauth/token`)
- `X-Org-Id: <orgId>` header

Scopes: `read` (default) and `write`. Write endpoints require a `write` token.

Error shape: `{ "error": { "code": "...", "message": "...", "request_id": "..." } }`

Pagination shape: `{ "data": [...], "next_cursor": "opaque_or_null" }` with `?limit` capped at 100.

Rate limit: 600 req/min burst, 20 req/s sustained per token. Returns 429 with `Retry-After`.

OpenAPI spec: `GET /api/v1/openapi.json`

## Documentation Maintenance

Certificate generation has two exclusive modes in `components/certificates/certificate-generate-panel.tsx`: policy mode selects one final policy plus a holder and includes every available coverage; requirements mode selects one `requirementSourceDocument` (or starts from one requirement connected to that source), derives the certificate holder from the source, and does not accept a primary policy or duplicate holder entry. `convex/lib/certificateRequirementPlan.ts` maps met or expiring-soon source requirements to the smallest set of final-policy targets and reports unmet/no-final-policy gaps with saved review rationale. Requirement-backed PDFs include only the ACORD lines needed by the requirements assigned to that target. `convex/certificates.ts` persists `requirementSourceDocumentId`, immutable requirement snapshots, and a batch ID on certificate parents, versions, legacy rows, and holds; requirement revisions change the reuse signature. Compliance source and requirement drawers can start fulfillment directly. Shared `generate_coi`, email attachment generation, and direct MCP/API calls use the same either/or contract, so web, Slack, iMessage, MCP chat, and email return every generated PDF without claiming gaps are satisfied. Requirement imports persist their source only after successful extraction, retain a zero-requirement source as an audit record for successful exact-duplicate imports, and deduplicate by normalized typed terms rather than title or line alone. The same extraction pass captures every explicitly identified certificate holder or recipient as normalized `certificateHolders` rows referenced in source order by `requirementSourceDocuments.certificateHolderIds`; `certificateHolderId` remains the primary compatibility pointer used by current single-holder certificate generation. Deterministic and agent reviews never retype generic limits as per-claim, per-occurrence, or aggregate proof; absent deductible, coverage-form, retroactive-date, provision, or form evidence remains unverified, while explicit mismatches remain not met. A persisted agent review is authoritative until the requirement changes. Public thread queries expose auditable tool activity but strip provider reasoning and reasoning steps; raw model thoughts must never render in customer chat. Next.js auth cookies use the same 30-day lifetime as Convex Auth's default refresh session so closing a browser does not sign the user out.
