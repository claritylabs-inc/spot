# Agent and MCP tool inventory

This reference lists the tools that Spot exposes to its operator agent, tenant-facing conversational agent, internal agent subagents, and OAuth MCP clients. It describes the current executable catalogs; it does not include deterministic controls, ordinary Convex functions, REST routes, or browser actions that are not model-callable or MCP-callable tools.

Spot supplies the tools active on each router step in `request.tools`; an empty array means no tools. `convex/lib/agentToolSelection.ts` selects available families through Jev, retains used or expanded families, assembles guidance, and falls back to all available families on failure or timeout. `expand_tools` accepts `families`, `family`, `tool_families`, or `tools` as a string or array (up to 50 names), resolves tool names to available families, and lists valid families on invalid input. It loads families for the next step without changing business records. Definitions carry name, description, and JSON input schema. Before each operator step, `getRunContextInternal` validates the active operator/thread and filters the registry by role, impersonation, and configured Google Workspace, Slack, Mapbox, and MCP access. Exact target authorization and approval are rechecked at execution; a tool's availability cannot authorize an arbitrary target. Family selection narrows the offered catalog; Spot does not force a business tool with `toolChoice`. Router-owned Jev selects among the offered tools or abstains, the generation model fills arguments, and Spot executes the calls. Operator generation uses this router selection too; Spot no longer forces `toolSelection: caller`.

`clRouterDecide` uses authenticated `/v1/decide` for typed Jev Choice/Noul decisions, with native probabilities and request-bound response validation. Classifications for forwarded-email direction, requirement import intent, certificate-holder matching and endorsement eligibility, carrier identity, compliance manual review, public company identity, policy intake, mailbox automation, Workspace PDF acceptance, intake question relevance/novelty (including exact-use-scoped vehicle/fleet inapplicability in `convex/actions/intakeVehicleRelevance.ts`), description-based industry suggestions, follow-up input primitive selection, Continue-triggered additional-question gates and evidence-based Boolean prefills, and prompt-injection screening use this path. Extraction and prose remain generation tasks; legacy classification/security generation settings remain schema-compatible but are not active UI routes. SDK generation callbacks reject classification instead of silently using generation. The chat policy-evidence classifier, deterministic completed-lookup check, and recovery generation are removed. Normal tool selection handles evidence retrieval; incomplete tool responses may still receive a tool-free final synthesis that cannot replay actions.

## Operator approval policy

Operator Settings (`/operator/settings`) owns one global **Approve all** switch,
shared by every operator and off by default. `operatorAgentSettings` stores the
setting; only active operators outside impersonation may change it, through the
portal API (never an agent tool or MCP tool). With it enabled, all new exact-gated
operator tool calls—including external sends, access/global changes, and
destructive actions—receive automatic fingerprint-bound approval and execute
without pausing the tool loop. The shared `requestOrExecuteToolInternal` path
serves web, email, Slack, and operator MCP. Role, OAuth write scope,
impersonation, preflight/source validation, cancellation, idempotency, and audit
checks remain enforced. Automatic approval is recorded on the existing
confirmation ledger and shown as Auto-approved; action execution rechecks the
current global switch. Existing pending confirmations still require a decision;
disabling the switch restores manual approval for new calls. Tenant approvals
are unchanged. References below to exact confirmation describe the default
manual mode; the global switch can satisfy that gate automatically.

Remaining reversible-write batches use `{items: [...]}` with 1–50 distinct
items, each with the corresponding single tool's fields, under one exact approval
bound to the full input. All items are validated before approval and again before
any write; one nested mutation commits changes, research scheduling and per-item
audits atomically. Approval cards list every item and supplied field, resolving
IDs to names without omitting IDs. Summaries over 20,000 characters require a
smaller batch. Results are compact `{results: [...]}` in input order.
`create_client_organizations` checks normalized exact-name duplicates within the
batch and against live clients and queues ordinary company research per client.
`research_brokers` queues research; it does not report research as completed.
`add_client_files` files only current-operator attachments from this conversation,
privately; repeated attachment aliases are rejected. `create_procurement_file_items`
requires distinct request/file pairs. Other updates require distinct record IDs.
`archive_procurement_proposals` archives even empty drafts, preserving records;
its single-item counterpart retains its existing empty-draft deletion behavior.
`cancel_email_drafts` accepts only drafts in this operator conversation, never
pending sends or sent/unknown-delivery messages. Bulk filing and cancellation
require exact approval even though their existing single-item tools run without
it. Existing single-item contracts and approval levels are unchanged.

Organization batches (`set_client_assignees`, `set_client_access_statuses`,
`set_client_feature_flags`) accept 1–50 items, one per distinct client, under one
exact approval bound to the complete input. Preflight validates every client and
assignee/flag before approval; execution revalidates and commits every change in
one nested mutation. A failure rolls back the entire batch. Each changed client
has its own `operatorAuditEvents` row with `metadata.domain: "operator_agent"`;
unchanged rows produce no write or domain audit. Approval summaries have a grouped
header plus every client/change, resolved to names, shared by web, Slack and MCP.
Slack splits long lists across sections without dropping rows. Single-item input,
output and approval behavior remain compatible.

## Inference execution

Operator tools run between durable router model steps, several per runner action.
Inference that outlasts its in-place wait yields and resumes the same job;
completed tool effects retain their existing idempotency keys. Exact messages
and the selected model route survive operator continuation.
Cancellation blocks subsequent tools and revokes the pending inference job.
Worker-loss outcomes are explicit and never cause automatic tool or model replay.
These lifecycle controls are internal, not new agent or MCP tools.

Operator model-facing tool outputs are bounded to 24,000 UTF-8 bytes per result and 128,000 bytes across durable tool history; histories with more result pairs than can retain safe status metadata stop with a context-limit reason. Oversized results carry `outputTruncated`, `bounded`, `originalBytes` and a paging/narrowing notice; failure state and intact cursors take priority. Existing execution audits remain server-side with their existing storage bounds. Raw tool-call text, channel markers and JSON tool envelopes are removed before final response persistence on every operator channel. Provisional operator reply text streams through the same sanitizer in `routerJobs.progress`; preparation/model/tool activity remains visible. Terminal failures include a fixed safe category and next step, with full diagnostics logged server-side; `get_operator_run` adds a structured `failure` on failed runs and omits raw `run.lastError`.

## Source owners and maintenance

- Operator-agent tools are defined only in `convex/lib/operatorAgentToolRegistry.ts`. `convex/lib/operatorMcpToolCatalog.ts` projects that registry into operator MCP and adds operator-run lifecycle tools.
- Shared tenant conversational tools are defined in `convex/lib/chatTools.ts` and executed by `convex/lib/agentToolExecutors.ts` plus `convex/lib/vendorComplianceTools.ts`. Policy lookup treats nullable optional filters as omitted, including the expiry window, before applying exact policy IDs and tenant scope.
- Channel-specific tenant tools are assembled in `convex/actions/processThreadChat.ts`, `convex/actions/handleInboundEmail.ts`, `convex/actions/handleInboundImessage.ts`, and `convex/actions/mcpChat.ts`.
- `convex/lib/channelAgentRunner.ts` owns shared conversational turn execution, tool-outcome auditing, and tool-free synthesis of incomplete responses. Web, Slack, email, iMessage, and MCP retain channel-local ingress, authorization, persistence, and delivery. Normal router tool selection handles policy lookups; there is no separate policy-evidence classifier, completed-lookup gate, or evidence-recovery generation.
- Discrete email tools and their shared executors live in `convex/lib/emailTools.ts`; no nested email model loop remains. The discrete mailbox family and shared account search/evidence helper live in `convex/lib/mailboxTools.ts`; every operation runs in the parent agent.
- Tenant OAuth MCP tools and their read/write, open-world, destructive, and idempotency metadata are defined together in the shared projection and compatibility metadata in `convex/lib/tenantMcpToolCatalog.ts`.
- MCP `tools/list` rechecks organization membership (`convex/mcpPrincipal.ts`) and filters the business catalog by principal and OAuth scope via `convex/lib/mcpCatalogScope.ts`. Client principals receive the tenant catalog allowed by their read/write scope; providers receive no tools; operators receive the registry filtered by operator role and scope. The server continues to enforce the authenticated principal and scope on every call. There is no MCP UI resource or workspace-launcher tool.
- MCP OAuth revocation accepts form-encoded access or refresh tokens (and legacy Bearer access tokens), invalidates the stored token pair, and rejects a supplied mismatched client ID before any change.
- MCP Events definitions and allowlisted filters/payloads live in `convex/lib/mcpEventCatalog.ts`. `convex/lib/mcpEventHttp.ts` exports the structural authenticated-principal adapter and `{ events: {} }` capability for endpoint composition; `convex/mcpEvents.ts` owns subscription authorization and the durable outbox, and `convex/actions/mcpEvents.ts` owns encrypted secrets, callback verification, and signed delivery. These are subscription protocol methods, not business-write tools.

When any source above adds, removes, renames, or materially changes a tool, update this inventory in the same change. Availability, capability, effect, required role, confirmation policy, execution boundary, and MCP access changes count as material.

## MCP Events

`events/list` discovers authorized webhook events. `events/subscribe` creates or
refreshes a deterministic, principal/client/resource-scoped subscription after
callback verification. `events/unsubscribe` idempotently revokes that matching
subscription. All three require a current read-scoped OAuth connection; they do
not grant write access, execute business tools, or satisfy exact approvals.
CLA-179 owns MCP 2.0 `server/discover` negotiation and endpoint composition.

The catalog exposes `compliance.status_changed`, `vendor.policy_expiring`,
`policy.ready`, `policy.review_required`, `procurement.request_updated`, and
operator-only `proposal.review_ready`. Domain mutations enqueue only matching,
allowlisted identifiers and transition labels. Client-hidden procurement
changes and private proposal content never reach tenant event payloads.
Compliance events reflect existing monitor cadence, not live carrier updates.

Delivery rechecks membership/operator activity, OAuth connection, target access,
expiry, and subscription generation. Callback validation is HTTPS/public-IP
only, with pinned DNS, no redirects, signed constant-time challenge verification,
a bounded verification cache, and safe `-32015` callback errors. A dedicated
32-byte base64 `MCP_EVENTS_ENCRYPTION_KEY` protects signing secrets. Settings
list only the owning actor's origin/scope/expiry and allow revocation. See
`docs/architecture/mcp-events.md` for limits and the unrun ChatGPT smoke workflow.

## Operator agent registry

Bulk exact-ID reads share `MAX_BULK_READ_IDS` (50, `convex/lib/operatorReadViews.ts`) with lower per-tool caps where a read is heavier (proposals 25, organizations 25, client files 20, Gmail threads 25); an oversized batch fails preflight as a recoverable input error naming the cap. Every free-text `query` field describes what it matches (literal substring, full-text, Gmail syntax or ranked keywords), and overlapping tools point to each other (list vs search vs get). The system prompt routes application and intake questions to procurement requests and a named email thread to one `search_team_inbox` call, then its `targets` in one `get_team_inbox_thread` call (other results only when `targets` is empty). Operator steps and the planner use the routed model's default reasoning effort. `OPERATOR_AGENT_QUALITY_HINT` in the runner is an unset hook for cl-router's pending model-quality requirement; when set, it is sent only to routers advertising its feature.

Operator steps use the shared family selector with a 15-family catalog. `team_inbox` holds shared team inbox reads and linking (`list_team_inbox_threads`, `get_team_inbox_thread`, `search_team_inbox`, `link_team_inbox_threads`); `outbound_email` holds drafting, suggested replies and sending; `operator_conversations` (formerly `threads`) holds operator chat history, never email. Retired family names map forward through `OPERATOR_TOOL_FAMILY_ALIASES` in stored `checkpoint.families`, message-audit carryover and `expand_tools` input. Jev answers one Noul per family in a single request; code loads every family at or above the proceed threshold (0.7), then uncertain-band families (`OPERATOR_FAMILY_LOAD_THRESHOLD`, 0.5) from most to least likely while the offered tools stay under `OPERATOR_FAMILY_TOOL_TOKEN_BUDGET` (28,000 estimated tokens, core included), because a missing family costs a full model step and an extra one only cached prompt tokens. The system prompt names the loaded families and tells the model not to expand them; the `expand_tools` description lists each family's tools. A run's first step omits `expand_tools` when its initial selection (intent, Jev or carryover) loaded any domain family, so the model acts with what it has; core-only first steps keep it, and it returns from the second step, appended after the step-0 tools so the cached tool prefix is kept. A resumed first step whose stored families were lost falls back to every family and keeps `expand_tools`, since its submission may have offered it. Timing rows record `expandToolsWithheld`, and the calibration query reports it as `expandTools.withheldOnFirstStep`. A request for families or tools that are all loaded returns `already_available` with the tools to call now, and new loads list their next-step tools and any `alreadyLoaded` families. `operatorPlanningCalibration.listRecentRunsInternal` reports each run's expand_tools calls, the families requested versus already loaded, the final family set and its first step's `pageContextPrefetch`. Starter intents keep their shortcuts and may declare prefetch reads (`operatorAgentIntentPrefetch`, run by `convex/lib/operatorIntentPrefetch.ts`): before a fresh run's first step the runner executes those plain reads through `executeToolInternal`, with the same authorization, audit rows and run-scoped idempotency keys as model calls, and hands the model the successful results as one answered tool step; failed or skipped reads are left to the model. A single-thread `reply_team_email` suggestion stores `focus.teamEmailThreadId` on its intent artifact and prefetches the compact thread, then its linked (or else addressed) request and procurement information. The thread's attached page context prefetches the same way (`convex/lib/operatorPageContextPrefetch.ts`, entries in `convex/lib/pageContext/`, one module per page group registered in `index.ts`): each entry declares its page types, the families every step must load, staged plain reads whose builders get `entityId`, the whole page (summary, href, related records), `relatedId(kind)`/`relatedLabel(kind)` and earlier results, optional hints derived in code from the results and page, and optional static notes shown every turn even when nothing is read. Prefetch reads are reads with no confirmation and no integration, executed as mutations, plus the action reads `lookup_policy`, `lookup_compliance_requirements` and `read_client_file`, which run through the runner's action executor with a 15-second timeout that fails open (web, MCP, Google Workspace and Mapbox tools call remote services, `search_team_inbox` asks Jev, `get_research_status` can wait and the `attach_*` tools change the conversation, so none are prefetched). A read flagged `partial` loads only part of the record; the prompt then lists what it lacks and the tool that reads more instead of saying not to read the record again. `team_email_thread` reads the full thread, then its linked or addressed request (`get_procurement_request` summary) and linked client (`get_organization`); other groups' entries, including some client list pages such as `operator_client_procurement` and `operator_client_policies`, live in their own modules, and page types without an entry (such as `pdf_document`) prefetch nothing. Intent and page reads form one answered step. Because the context is sticky, the page's record is read on the first run after it was attached or changed, or while none of the last eight assistant turns within 24 hours (the family-carryover window) holds a successful read of the entity by the entry's first-stage tools or a successful prefetch of the same page (page reads are audited as `prefetch_page_<tool>`, matched to the page context stored on the operator message the turn answered, so entries whose reads take an orgId or related record are suppressed too); a starter intent that already read the entity covers it. The system block then says the record is loaded (do not re-read or search for it), or that it was read on an earlier turn, and lists the hints: for an email thread, the outside sender (the original sender of a forward), their company domain, a subject or signature line naming that company, and its links or "not linked to a client or procurement request". The block frames the page summary as of attach time (drawers or selections it names may have closed) and keeps untrusted-data semantics; write targets are still revalidated through tools. Page contexts may carry `related` records (`{kind, id, label?}`, at most 10; an entry with an invalid kind or id is dropped, never rejected). Resumed durable steps offer all available families, and tools used or expanded earlier in the run remain loaded. Follow-up turns retain used and explicitly expanded families from the previous eight assistant turns within 24 hours, reconstructed from existing message audits rather than a thread-wide mutable cache. A new conversation, the turn window or expiry resets that carryover; current role, impersonation, email restrictions and integrations still determine actual availability. Declarative dependency lookups offer `list_operators` and `lookup_client_wiki` with organizations, and `list_client_files`, `get_procurement_request` and the team inbox reads with outbound email, without loading unrelated family writes. Operator MCP exposes the currently configured, authorized catalog; disabled Google Workspace, Slack, Mapbox and external MCP tools are omitted using the same registry availability filter and live configuration checks as the runner. The `expand_tools` control exposes additional families on demand and is not a business write; the registry still rechecks role, integration, exact target, and approval at execution. Command email without available raw-message authentication carries a durable `emailReadOnly` restriction: only read tools are selected, external MCP is excluded, and every execution path rechecks the restriction. The reply may draft wording, but cannot create saved drafts or perform writes and sends. For authenticated command email, the final answer is also delivered automatically. Outbound email tools require a separately requested email action; a reply-only or no-change request must not save a draft. Procurement email tool argument names remain supported, but their IDs refer only to `teamEmailThreads`; legacy storage IDs no longer resolve.

The [operator activity icon inventory](docs/design/operator-tool-icons.md) groups
every operator tool by its browser activity icon. Web research records a bounded
target label at execution start: a hostname for one site, or up to ten public
site URLs for overlapping favicons and a website count. Generic queries keep a
short readable label. Setup traces retain factual outcomes (loaded tool groups,
configured model, planning decision and plan size); identical completed outcomes
are grouped only in the UI. These are observed activity metadata, not model
reasoning. Router callbacks still accept only their existing stage/name contract.

Submitted company facts live in `organizations.intakeBusinessProfile` and request facts in `intakeSubmittedApplication`; research and authored notes remain company Markdown. `update_client_business_profile` is the preferred exact-approved operator tool for company-field edits and document imports. Read `get_organization` with `include: ["businessProfile"]` or `lookup_client_wiki` first for `businessProfile.submittedAt` (0 if absent); supply `expectedVersion` and only changed typed answers/details. Omitted fields are preserved; supplied addresses, revenue objects and lists replace that whole field. Its provider schema leaves `answers`/`details` as free-form objects (key names only); `describe_record_fields` returns the shapes, and the strict validator rejects unknown keys, bad enums and malformed addresses before approval, naming the allowed keys at the offending path. It shares the profile editor’s operator-only, impersonation-protected, revision-checked writer and leaves submitted request snapshots and Markdown untouched. `update_organization_profile` accepts only name and website; `get_organization` returns compact identity by default; `include: ["businessProfile"]` adds the client’s typed business profile and `include: ["websiteTech"]` its best-effort `websiteTech` scan (detected payment, hosting, email and SaaS signals plus quoted vendor/region disclosures from the company’s own pages, and `websiteTech.browse.skills`: up to 40 browser procedure outcomes such as email verification, each with name, version, `succeeded`/`blocked`/`failed`/`skipped` status, a redacted summary and step count; absent on older scans or when the router reported none). Operator and tenant policy lookups and COI generation use policy evidence and policy overrides, with no company-profile fallback. `update_client_wiki` / `write_company_wiki` edit prose only; they cannot amend submitted application facts. `lookup_client_wiki` includes the typed business profile, and procurement request reads include the accepted structured application. Application amendments use owner intake edits and resubmission.

Spot-owned brands and domains represent Spot. Provider registration, profile updates, outreach, proposal filing, review confirmation, and selection reject those identities at preflight and execution; provider directory/search results exclude existing matching rows. Exact `get_organization` reads label historical matching rows `spot`. Records and history remain stored; this classification never grants operator access.

Operator attachment intake has no file-count cap across web, email, Slack,
iMessage, and MCP. Per-file, aggregate-byte, channel transport, and emitted
router-asset budgets still apply; `run_operator_task` accepts attachment arrays
without a count restriction.

Operator email confirmation replies preserve the current exact approval and
waiting run; approval still requires the portal controls. Quoted email history
is not a new operator instruction, and forwards nested in that history are not
fresh source messages. The read-only `scan_workspace_mailbox` tool excludes Spot Operator's own outgoing summaries from collected evidence.

The operator registry is defined in `convex/lib/operatorAgentToolRegistry.ts`. Writes require an exact, fingerprint-bound confirmation except for the registered private attachment-filing action (`add_client_file`). Exact-confirmed tools run the shared reference preflight in `convex/lib/operatorAgentConfirmationPreflight.ts` before the confirmation is shown, and the write revalidates the same references at execution. Registry schemas expose executable ACORD LOBCd, ISO country and US state/Canadian province enums plus ISO dates, email addresses, HTTP(S) URLs, replacement-list semantics, and explicit omit-versus-null guidance instead of relying on prose guesses. `mutation` and `action` identify the Convex execution boundary, not whether the operation writes data. The versioned browser/agent procurement parity contract lives in `convex/lib/procurementCapabilities.ts`.

Operator web chat, authenticated inbound email, and the internal Slack adapter all enqueue into the same operator runner, which registers this complete registry without a channel-specific tool allowlist. Each channel still keeps its own transport authentication, identity resolution, thread persistence, and attachment ingestion. For Slack, customer connection and Slack Connect binding resolution takes precedence, and every invocation still requires an active operator profile linked to the exact host-workspace Slack identity; Convex applies no channel allowlist, type, privacy, sharing, or membership gate after that identity is resolved. Operator MCP exposes the same registry and executes the same service-backed tools, so “Slack agent” behavior is Spot-agent behavior rather than a Slack-only catalog. Procurement forwarding email is ingested deterministically into the same canonical request/email/artifact records before the agent reads it, rather than granting the tenant email agent access to operator-private proposals.

Operator command email uses the shared `agent@team.spot.insure` inbox. Its Resend thread ID maps to a private operator conversation after active-operator resolution and aligned full-body DKIM verification of original MIME from Receiving. Explicit authentication failures reject the message. Only unavailable raw MIME permits a durable read-only run; writes, sends, saved drafts and external MCP calls remain blocked after continuation. Responses go only to the resolved operator's canonical login address. Legacy `operator(+t)@agent.spot.insure` addresses retain their authenticated path. Quoted senders, copied recipients and unverified Reply-To addresses never gain access, and email replies cannot approve exact writes. Delivery retries the frozen response rather than the tool loop.

### Operator skills

Operators import Claude Code / Codex skills (a folder with `SKILL.md` front matter `name` and `description`, plus optional references, scripts and assets) in Settings → Skills (`/operator/settings?section=skills`). `convex/operatorSkills.ts` owns tables `operatorSkills` (one row per skill: name, description, scope `personal` or `shared`, owner, enabled, revision, file count, bytes, hasScripts, source label, import warnings, imported/updated by and at) and `operatorSkillFiles` (path, size, hex SHA-256, kind `instructions`/`reference`/`script`/`asset`, text flag, storage ID). `convex/lib/operatorSkills.ts` holds the shared parsing and limits (200 files, 5 MiB, 64 KiB SKILL.md body, name `^[a-z0-9][a-z0-9-]{0,63}$` normalized from front matter, description up to 1,024 characters; `.git`, `node_modules`, `__pycache__`, `__MACOSX` and `.DS_Store` are skipped); the browser previews with it and `importSkill` re-runs every check on the uploaded bytes. The block states that skills are the operator's procedures and guidance only: they cannot grant tools, skip approvals, change authorization or override system rules, and, while cl-router does not advertise `exec` (cached `/v1/capabilities`), that scripts cannot run, so the agent says so instead of pretending; once it does, it states that scripts run only through `run_skill_script` with the operator's approval of each run. Skills with scripts carry ` [scripts]` on their line. Each call lands in `agentActionAuditEvents` with target `operator_skill` and the skill name (and path). `run_skill_script` is offered only when an enabled skill has scripts. Its approval card is `Run <script> from skill <name>` followed by `- Arguments:`, `- Working files:` and `- Network:` bullets, and its `sourceFingerprint` binds skill id and revision, argv, the stdin hash, input file IDs, network and timeout; approval and execution re-resolve the run and refuse any change. Execution uses the approval as the router invocation key, so a retried execution reconnects instead of running again; an outcome that may have started is reported as unknown and never replayed. Scripts never run without approval, and `run_skill_script` never files outputs in client records (`add_client_files` does, on request). See `docs/architecture/operator-skills.md`. The tools are `agentOnly`: excluded from operator MCP `tools/list` and refused by its `tools/call`, and absent from the client agent and tenant MCP.

an honest `bounded` flag. The top-level `profiles` list deduplicates grouped
results. Its limit bounds scanned providers, so filtered pages may be empty. Profile/contact/activity and
research details are available through `get_broker_network_profile` (v4). Its
operator-only `submissionDefaults` returns `{defaults, bounded}`, with at most
200 coverage records and a 1 MB read budget. Each record contains instructions,
minimum-information questions and reusable answer guidance, plus form metadata
and storage URLs; file bytes are never embedded. Operators curate these standards
in the provider's Submission defaults view or from an inbox message/attachment.
Preparing a future submission should follow the saved coverage process. This
read does not attach documents, populate client answers, send mail or bypass any
existing approval. Active operator and external-provider authorization are
rechecked when the defaults are read; provider portal members cannot access them.

Provider batch tools accept at most 50 homogeneous reversible writes. Every item
is validated before approval and revalidated in a child mutation, which rolls
back all profile/outreach/audit writes and research scheduling on failure.
Summaries enumerate all items and patches. Ensure does not edit matched profiles;
it reuses existing request/provider outreach and returns each input, outcome,
orgId and optional outreachId. New profiles retain the single-create enrichment
semantics; matched providers need a separate `research_broker` approval to rerun
research. Identity matching scans at most 5,000 active provider organizations and
fails closed if the bound is exceeded. No schema/index changes are required.

Operator context management: `compact_context` v1 is a core read tool
(`operator.threads.read`, operator role, no confirmation, mutation boundary).
Optional `keepRecentSteps` (1–12, default 4) and `focus` (up to 1,000 characters)
request working-context compaction on the next durable iteration. It retains
complete recent call/result exchanges and exact reference metadata. Direct MCP
invocations return `not_applicable` because they have no model working context;
use the tool inside `run_operator_task`. Notes cannot authorize writes or change
confirmation hashes. Summary failures fall back to deterministic notes; if those
do not fit the hard limit, the original context is retained when it still fits.
Only when neither fits does the run fail. Automatic compaction estimates the
full system, offered schemas and messages; checkpoints retain mode, count,
before/after estimates and skipped-attempt status.
Completed operator turns schedule a bounded rolling conversation summary,
using the existing `summary` model task and thread-continuity helpers. See
[operator context compaction](docs/architecture/operator-context-compaction.md).


Operator outbound email uses the calling operator’s Resend team inbox. The direct
Google SMTP rollout is retired; there are no connect, select-sender, resume or SMTP
send paths. Existing tools keep exact sender/content/recipient approval. A previous
Google draft must be reviewed under the Resend identity; never replay an unknown
send. Read-only IMAP sync and historical message/draft reads remain available for
old Google correspondence. `/operator/email-health` redirects to Inbox. See
`docs/architecture/team-email.md`.

Provider relationship labels retain their stored enum keys: `prospect` is Cold, `active` is Active Relationship, and `blacklisted` is Do Not Contact. Previously contacted `inactive` providers also use cold copy. Initial provider outreach introduces the authenticated operator and Spot only for cold relationships; active relationships get a direct quote request. New provider drafts use we/us/our for the coordinated client request, include every requested coverage line and known limit in the quote-request sentence, and never imply Spot is the insured. Current relationship status is read at send-time claim; Do Not Contact remains blocked at launch and before delivery. Saved drafts and unknown delivery outcomes are never rewritten or replayed by a label/copy change.
